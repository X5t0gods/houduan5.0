## 1 总体判断：这个项目的真实难点在哪

128 个接口看起来是"体力活"，实际风险分布很不均匀。把精力按下面的权重分配：

```
难度 ▲
     │  ● 收银结算 T1（事务 + 幂等 + 成本快照 + 促销叠加）
     │  ● 促销引擎（优先级 / 互斥 / 叠加上限，算错就是顾客纠纷）
     │  ● 库存一致性（流水为准 + 条件更新防超卖 + 勾稽恒等式）
     │  ● BI 异步任务（CPU 密集，不能阻塞事件循环）
     │  ──────────────────────────────────────────
     │  ○ 采购收货 T2（表多但流程线性）、盘点 T3
     │  ○ 报表聚合（SQL 写对就行，慢就预聚合）
     │  ──────────────────────────────────────────
     │  · 系统管理 / 商品 / 会员 / 供应商 CRUD（约 60 个接口，模式高度重复）
     └──────────────────────────────────────────────────────────► 数量
```

三条主线必须从第一天就守住：

1. **P0 生命线**：认证 → 商品 → 收银 → 库存。这四块跑通，系统就能演示"开店营业"，答辩的底线就保住了。
2. **答辩亮点链**：`BI 挖掘规则 → 采纳规则 → 自动生成促销 → 收银台推荐`。这条链路串起了"数据 → 算法 → 业务动作"的完整闭环，是论文最值钱的部分。
3. **可自证的一致性**：库存勾稽恒等式、进销存恒等式、会员储值/积分恒等式。这三条 SQL 能把"数据准不准"从主观描述变成客观证据。

## 2 技术架构

### 2.1 分层架构

严格遵循需求文档 NFR-M-01 的四层约束（router / service / repository / model），**层间单向依赖、禁止跨层调用**：

| 层 | 目录 | 职责 | 禁止事项 |
| --- | --- | --- | --- |
| 接入层 | `app/middleware/` | CORS、`request_id` 注入、访问日志、全局异常兜底 | 写业务逻辑 |
| 接口层 | `app/api/v1/` | 参数校验（Pydantic Schema）、权限声明、调 service | 直接查库、写 SQL、写业务分支 |
| 业务层 | `app/services/` | 用例编排、事务边界、业务规则、状态机 | 拼 SQL、感知 HTTP |
| 仓储层 | `app/repositories/` | 数据访问（ORM 查询 / 原生 SQL）、数据范围过滤 | commit、写业务规则 |
| 模型层 | `app/models/` | SQLAlchemy 2.0 声明式映射（61 张表） | 业务方法 |

横切能力（配置、日志、权限、幂等、单号、导出、定时任务）放在 `app/core/` 与 `app/common/`，被各层按需引用。

### 2.3 关键技术决策

每条按「结论 → 理由 → 代价」写，便于直接搬进论文的"概要设计"章节。

#### 决策 1：数据库访问同步还是异步（**最需要先拍板的一条**）

**结论**：推荐 **同步 SQLAlchemy 2.0 + PyMySQL，接口用 `def`**（FastAPI 自动丢进线程池），**全项目二选一，绝不混用**。

**理由**：

- 需求文档的异步收益（NFR-P-10 只要 10 个收银终端并发）在这个量级用不上，而 128 接口 + 61 表的工作量下，异步的隐性成本很高；
- 异步 ORM 的坑集中在：无懒加载（N+1 变显式查询）、会话生命周期更易错、`BackgroundTasks` 与异步会话叠加容易出诡异 bug、调试栈难读；
- 真正需要"异步"的地方（BI 挖掘、Excel 导出、备份）是 **CPU 密集**，异步数据库驱动对此毫无帮助，反而必须丢线程/进程；
- CON-01 说"必须为 FastAPI + ASGI 异步架构"——**FastAPI 本身就是 ASGI 异步框架**，DB 调用走 Starlette 线程池不违背该约束，`NFR-P-01 500ms` 依然轻松达标。

**代价**：论文里"异步高性能"这个卖点要换种写法（写成"ASGI 异步框架 + 热点路径可异步化预留"）。若导师明确要求异步 DB，就**全量异步**（`asyncmy` + `AsyncSession` + `async def` 接口 + `AsyncEngine`），不要一半一半。

#### 决策 2：ORM 与原生 SQL 的分工

**结论**：两者都要，边界清晰，**只允许出现在 repository 层**。

| 场景 | 选型 | 原因 |
| --- | --- | --- |
| 单表/少数 JOIN 的 CRUD、事务写入 | ORM（`Mapped[]` 声明式 + `select()`） | 类型安全、可读、关系清晰 |
| 12 个报表聚合、进销存勾稽、看板 | 原生 SQL（`text()` / `func` 聚合） | ORM 表达复杂聚合会退化成 N+1 |
| BI 事务集抽取（FRS-BI-001） | **必须原生 SQL + pandas** | 需求文档明确要求"避免在 Python 层逐单循环" |
| 库存/储值勾稽校验 | 原生 SQL | 恒等式要能直接贴进论文与验收报告 |

#### 决策 3：统一响应体与业务错误

**结论**：业务失败一律 **HTTP 200 + 非 0 `code`**；HTTP 状态码只表达传输/认证层（401/403/404/500）。

- **登录失败也必须 200 + 1002**。前端 `request.ts` 的响应拦截器只在 HTTP 401 时清登录态并跳登录页；若后端把"密码错误"返回 401，用户会被莫名踢回登录页。
- 实现方式：全局异常处理器统一兜（`BusinessError → 200 + code`；`RequestValidationError → 200 + 2001`；`HTTPException → 保留原状态码`）。
- 文件流接口（4 个导出 + 小票）**不包 `ApiResult`**，直接 `StreamingResponse`，否则前端解析成 JSON 会崩。

#### 决策 4：权限与数据范围

- **29 个权限码字符串必须与前端一字不差**（`goods:product:list`、`pos:use`…）。`/auth/me` 的 `permissions` 决定左侧菜单能否渲染，错一个字母 = 一整个菜单消失。
- 写接口用 `require_perm("xxx")` 依赖逐条校验，**不依赖前端 `v-permission`**（那只是体验优化）。
- `data_scope`（ALL / STORE / DEPT / SELF）的过滤条件统一在 **repository 层注入**，FRS-AUTH-012 明确禁止路由层手写 `where`。

#### 决策 5：幂等

| 接口 | 幂等实现 | 现状 |
| --- | --- | --- |
| `POST /sales/trades` | `sal_trade.request_id` 唯一索引 | ✅ 表已支持 |
| `POST /members/{id}/recharge` | 需补 `mem_balance_flow.request_id` + 唯一索引 | ⚠️ 需改表 |

标准三步（并发安全）：

1. 先按 `request_id` 查，命中则**直接回放首次结果**，不重复执行；
2. 未命中则正常执行并写入；
3. 捕获 `IntegrityError`（并发同一 `request_id` 撞唯一索引）→ 重新查询并返回首次结果。

注意：前端**只对** `/sales/trades`、`/sales/trades/*`、`/members/recharge` 三段路径自动注入 `request_id`（`request.ts` 的 `IDEMPOTENT_PATHS`）。其他接口不要指望收到幂等键。

#### 决策 6：单号生成

**结论**：新增 `sys_no_seq` 表，用 MySQL 的 `LAST_INSERT_ID(expr)` 原子自增，**单条 SQL 无显式行锁**：

```
UPDATE sys_no_seq SET current_val = LAST_INSERT_ID(current_val + 1)
 WHERE seq_key = :key AND seq_date = :today;   → 再 SELECT LAST_INSERT_ID()
```

- 当天首单：`INSERT IGNORE` 初始化 `current_val = 0` 后重试；
- 覆盖 14 类单据（XS / CG / SH / CT / TH / PD / BS / DB / JB / CZ / 商品 P / 会员 M / 供应商 S / 批次）；
- **绝对禁止 `SELECT MAX(no) + 1`**（文档 8.2 明确禁止，并发必重号）。

#### 决策 7：金额、数量与序列化

| 项 | 规定 |
| --- | --- |
| 数据库 | 金额 `DECIMAL(12,2)`、数量 `DECIMAL(12,3)`（DC-01/02） |
| Python 运算 | 全程 `Decimal`，**禁止 float 参与金额运算**（0.1+0.2 的经典坑） |
| 舍入 | `quantize(Decimal("0.01"), ROUND_HALF_UP)`，与抹零参数一致 |
| 出参 | ⚠️ **Pydantic v2 默认把 `Decimal` 序列化成字符串**（`"12.30"`），而前端类型是 `number` 且直接参与运算 → 响应模型显式声明 `float` 或用 `field_serializer` 转 float。**这是必踩的坑，建议阶段 0 就定死规范。** |

#### 决策 8：事务边界（T1–T4）

- `commit` / `rollback` **只出现在 service 的用例方法**里，一个请求一个事务；repository 只负责 `flush`。
- 事务内**不做 HTTP 调用、不发消息、不写文件**（小票渲染、备份落盘都在事务外）。
- 只读接口不显式开事务。
- T1 收银必须在**一个事务**内完成：幂等校验 → 业务校验 → 销售主单 → 明细（含商品名/成本价快照）→ 支付明细 → 扣库存 → 写库存流水 → 会员余额/积分 → 累计消费与等级 → 促销统计。

#### 决策 9：并发控制优先用数据库条件更新

| 风险 | 措施 |
| --- | --- |
| 同商品被两台收银机同时卖出（超卖） | `UPDATE inv_stock SET quantity = quantity - :q WHERE store_id=? AND product_id=? AND quantity >= :q`，`rowcount = 0` → 抛 `7004` |
| 并发扣会员余额（余额变负） | 同样条件更新 `WHERE balance >= ?`，`rowcount = 0` → `7002` |
| 重复提交结算 | 唯一索引 + 决策 5 |
| 单据状态并发流转 | 状态机校验 + `WHERE status = 'DRAFT'` 条件更新（`rowcount = 0` → `4001`/`5002`） |

设计倾向：**用数据库原子性解决并发，而不是应用层加锁**（单机部署下应用层锁更复杂、易死锁）。

#### 决策 10：无 Redis 下的缓存与预聚合

方案约定不引入 Redis（05 文档 1.3），替代手段：

| 需要缓存的东西 | 替代方案 |
| --- | --- |
| 图形验证码 | `sys_captcha` 表 + `expire_at`，APScheduler 定时清理（已定） |
| 看板与 12 个报表 | `bi_daily_stat` 预聚合表（APScheduler 每夜重算）+ 短 TTL 内存缓存 |
| 收银台关联推荐（≤100ms） | `bi_recommend_cache` 表，**服务启动时全量加载进内存**，挖掘任务完成后重载 |
| 促销规则 | 启动加载 + 增改删时失效重载（数据量小） |

⚠️ **进程内缓存与多 worker 不兼容**：uvicorn 开多 worker 时各进程缓存不一致。门店级并发下单 worker 足够，若要开多 worker，则只把"低频变更"的数据放进程内。

#### 决策 11：BI 任务的执行方式（异步方案的最大风险点）

- `POST /bi/analysis/run` **立即返回** `{task_id, status: "PENDING"}`，前端轮询 `GET /bi/tasks/{id}`；
- 真正计算（`mlxtend` 的 apriori / fpgrowth + one-hot 编码）是 **CPU 密集阻塞**，必须丢到 `ThreadPoolExecutor` / `ProcessPoolExecutor`（或独立 worker 进程轮询任务表）；
- ⚠️ **绝不能写在 `async def` 里直接跑**——会卡死整个事件循环，所有接口一起超时（这是"选异步方案"时最容易翻车的地方）；
- `cost_ms` 用 `time.perf_counter()` 精确计时并落 `bi_analysis_task`（**论文实验章节的核心指标**）；
- 任务失败要把 `error_msg` 落库（`BI_10001` 数据不足 / `BI_10002` 参数非法）。

#### 决策 12：Alembic 与既有 SQL 脚本的关系

- `01_schema.sql` 是**结构真相源**（61 表 + 86 外键，已验证可重复执行）；
- **不要用 `alembic revision --autogenerate` 反向生成建表脚本**，会与既有脚本在索引名、注释、外键顺序上产生差异；
- 正确姿势：手工跑 `01_schema.sql` + `02_init_data.sql` 建库 → `alembic stamp head` 打基线 → 之后的变更才用 autogenerate 生成迁移；
- **ORM 模型必须与 schema 逐列对齐**（列名、类型、可空、默认值）。建议写一个 `scripts/check_models.py`：把 `Base.metadata` 与 `information_schema.columns` 做差集比对，确保 61 张表不漏不错——这个脚本本身也是论文里"模型与库结构一致性"的证据。

## 3 开发步骤（12 个阶段）

每个阶段都给了「目标 / 交付物 / 验收口径」。**验收口径即联调动作**——每完成一个阶段，前端就能点开对应页面看一眼，这是控制返工最有效的手段。

### 阶段 0 · 工程骨架

- **目标**：一个能跑起来、有规范空壳的服务。
- **交付物**：`pyproject.toml`、`.env.example`、配置加载、日志（带 request_id）、`ApiResult`/`PageResult`、`BusinessError` + 全局异常处理器、CORS、`GET /api/v1/health`、Swagger 中文 title/description、`ruff` 配置。
- **验收**：`/docs` 可访问且接口有中文说明；`/api/v1/health` 返回 200 且 ≤ 50ms、含 DB 连通状态。

### 阶段 1 · 数据层（61 表 + 序列表）

- **目标**：模型与库结构严格对齐，单号可并发安全生成。
- **交付物**：8 个域文件的 ORM 模型（61 表）、`Base`/`engine`/`SessionLocal`、Alembic 基线（`stamp head`）、**新增 `sys_no_seq` 表**、**`mem_balance_flow.request_id` 补列**、`check_models.py` 比对脚本、`seed` 造数脚本雏形。
- **验收**：`check_models.py` 零差异；单号生成器并发 100 次无重复；改表后"从零重建"验证通过并同步更新 `db/README.md` 缺口清单。

### 阶段 2 · 认证与权限（6 接口）

- **目标**：登录能进、菜单正确、越权拦住。
- **交付物**：`/auth/captcha`（Pillow 出图 → `sys_captcha`）、`/auth/login`（bcrypt 校验 + 失败计数锁定 5 次/15 分钟 + 登录日志）、`/auth/me`（角色 → 权限码集合）、`/auth/refresh`、`/auth/logout`、`/auth/password`、`require_perm` 依赖、`data_scope` 注入骨架。
- **验收**：5 个演示账号（`123456`）全部可登录；`/auth/me` 返回的权限码个数为
  **`admin` = `["*"]`（通配符，前端 `stores/user.ts` 靠它判定超管）、`manager01` = 26、`cashier01` = 6、`stocker01` = 9、`buyer01` = 26（一人多岗取并集）**；
  前端左侧菜单按角色正确渲染、页头显示中文角色名；登录失败返回 HTTP 200 + 业务码（**不是 401**）；未登录 401、无权限 403。

> ⚠️ 口径提醒：`db/README.md` 里的「32 / 29 / 7 / 11 / 10」是 `sys_role_permission` 的**关联记录数**（含 3 个目录节点 `menu:*`），
> **不是接口返回值**。`/auth/me` 只返回 `perm_type = 2` 的功能权限码（29 个），目录码不返回。
> 另：`sys_permission.perm_type` 实际只用 `1`（目录）和 `2`（功能权限），**不存在 `3`**，接口文档与建表脚本注释里的「3 按钮」未被使用。

### 阶段 3 · 基础数据与商品（13 接口）

- **目标**：商品能建档、能检索、能扫码、能批量导入。
- **交付物**：`/units`、`/categories`（三级树 + 被引用只能停用）、`/products` CRUD（含 `category_name`/`unit_name`/`stock_qty` 关联字段）、`/products/barcode/{barcode}`、`/products/import`（逐行校验 + 错误报告）、价格变更写 `prd_price_history`。
- **验收**：商品列表/详情/建档页可用；重复条码返回 2002；售价 < 进价返回 2003 并在前端二次确认后成功；导入返回 total/success/failed/errors。

### 阶段 4 · 收银主链路（14 接口）— **优先级最高**

- **目标**：完成一笔真实交易。
- **交付物**：`/sales/cart/resolve`（走条码索引，P95 ≤ 200ms）、`/sales/cart/calc`（**促销引擎**）、`/sales/trades`（**事务 T1**）、销售单查询/详情、`/sales/trades/return`、作废、挂单/取单、小票数据、`/sales/sessions/current` + `close`。
- **促销引擎行为基准**：**以 `qianduan/src/mock/promotion-engine.ts`（160 行）为唯一行为基准**，逐条对照实现。特别注意：
  - 计算顺序按 `priority` 升序：`SPECIAL(1) → DISCOUNT(2) → COMBO(3) → FULL_REDUCE(4) → FULL_GIFT(5) → COUPON(6) → MEMBER(7)`；
  - `is_stackable = 0` 的促销互斥（命中一个后其余跳过）；
  - 满减基数需**扣除已生效优惠**（用 `累计优惠后的余额` 与门槛比较）；
  - ⚠️ **`MEMBER` 类型不放进计算**（Mock 明确注释：会员等级折扣由前端 store 单独汇总，后端再返回会重复扣减）。上线前必须用收银台实测验一遍，这是最容易多扣钱的地方。
- **验收**：走通一笔"会员 + 促销 + 混合支付"的交易；库存与流水一致；关闭前端 Mock（`VITE_USE_MOCK=false`）后前端行为与 Mock 完全一致；重复提交同一 `request_id` 不产生第二笔单据。

### 阶段 5 · 库存（14 接口）

- **目标**：库存账实可对。
- **交付物**：`/inventory`、`/inventory/flows`(+导出)、`/inventory/warnings`（缺货/积压/临期三类）、盘点单全套（`checks` + `items` + `submit` + `audit`，**事务 T3**，冻结 `snapshot_qty`、差异必填原因 `5001`、审核生成 `CHECK_ADJUST` 流水）、报损、调拨。
- **验收**：库存流水勾稽 SQL 返回空集；盘点审核后库存与流水一致；进销存恒等式 `期初 + 入 − 出 = 期末` 成立。

### 阶段 6 · 采购与供应商（14 接口）

- **交付物**：采购单 CRUD + 审核/作废（状态机）、`/purchases/{id}/receive`（**事务 T2**：收货 + 库存 + 流水 + 批次 + **移动加权平均成本重算**）、`/purchases/direct-receive`（无单入库）、采购退货（冲减应付）、供应商 CRUD、对账单、付款登记。
- **验收**：建单 → 审核 → 收货 → 库存增加 → 成本按公式重算正确 → 对账金额一致；单据状态非法时返回 4001、超收返回 4002。

### 阶段 7 · 会员与促销（14 + 12 接口）

- **交付物**：会员 CRUD、`/members/search`（**手机号后 4 位模糊匹配**，收银台 F4 用）、等级、**充值（事务 T4 + 幂等 + 本金/赠送双轨）**、储值/积分流水、积分调整、消费档案、脱敏导出；促销 CRUD、启停、`simulate`（试算）、`effect`（效果分析）、优惠券、`match`。
- **关键规则**：消费**先扣赠送余额再扣本金**；退款**只退本金**（防"充 100 送 20 → 退款套 120"）；积分抵扣上限为应收的 50%（可配）。
- **验收**：充值/消费/退款的流水与余额完全勾稽；会员报表的储值余额总额 = `Σ balance + Σ gift_balance`。

### 阶段 8 · 报表（12 接口）+ 预聚合

- **交付物**：`/reports/dashboard`（一次返回全部卡片）、销售日报/时段、商品排行、品类、毛利、滞销、进销存、采购、会员、收银员、通用导出；`bi_daily_stat` 预聚合 + APScheduler 夜间重算。
- **必须遵守**：
  - `/reports/sales/hourly` 返回 **24 条**，无数据时段**补 0**（否则前端折线断裂）；
  - 毛利必须用 `sal_trade_item.cost_price` **成本快照**，不能用商品当前进价（历史毛利不能被后续进价污染）；
  - `/reports/inventory/inout` 的 `期初 + 入库 − 出库 = 期末` **必须成立**，前端会把不成立的行标红。
- **验收**：日报销售额 = 当日销售单金额之和（抽样核对）；看板首屏 ≤ 3s；导出 Excel 可打开且行数正确。

### 阶段 9 · 智能分析（9 接口）— **论文亮点**

- **交付物**：`/bi/analysis/run`（异步 + 立即返回 task_id）、任务列表/详情（轮询）、`/bi/rules`（含 `interpretation` 业务解读、`suggestion` 建议）、`/bi/recommend`（**请求字段是 `product_ids` 复数数组**）、`/bi/rules/{id}/adopt`、`/bi/compare`（Apriori vs FP-Growth 耗时对比）、`/bi/forecast`、`/bi/replenish`。
- **实现要点**：事务集抽取走 SQL + pandas 构造 one-hot；挖掘丢线程/进程（见决策 11）；`cost_ms` 精确记录；推荐结果按 `score = lift × confidence` 降序、排除已在购物车的商品、无规则时**静默降级**（不得影响收银）。
- **验收**：样例数据上能挖出规则且支持度/置信度/提升度与手工计算一致；`/bi/compare` 两算法产出**等量**频繁项集与规则（差异只在耗时）；收银台加购后 1 秒内出现推荐且可一键加购。

### 阶段 10 · 系统管理（20 接口）

- **交付物**：用户 CRUD + 重置密码 + 启停、角色 CRUD + 权限树（内置 `ADMIN` 不可删）、参数列表/修改（记日志）、字典、操作日志、登录日志、备份列表/立即备份/恢复（`confirm_text == "RESTORE"`）、`/system/info`（版本/启动时间/uptime/DB 状态）。
- **验收**：权限树勾选后保存生效；改一个系统参数能在收银台看到行为变化（如临期天数）；备份文件能生成且记录落 `sys_backup`。

### 阶段 11 · 测试、造数与部署

- **交付物**：
  - `pytest`：单元（促销引擎纯函数、成本重算、单号生成、金额舍入）+ 集成（结算事务回滚、幂等、权限、状态机）；
  - **造数脚本**（`scripts/seed.py`）：`02_init_data.sql` 只有 20 个商品且**无历史交易**，而 BI 挖掘与 `/bi/compare` 实验要求"5 万笔交易、3000 SKU、min_support=0.01、≤60s"。必须生成可控规模的合成数据（含刻意植入的购物篮共现模式，便于验证规则正确性）；
  - 性能压测（locust / k6）覆盖 `/sales/cart/resolve`、`/sales/trades`、`/inventory`，验证 NFR-P-01/02/04/10；
  - `Dockerfile` + `docker-compose.yml`（api + mysql）+ Nginx（静态 + 反代）+ `Makefile`。
- **验收**：AC-18「干净环境 `docker-compose` 一键部署并跑通收银」通过；NFR-P 指标在测试报告中全部达标。

| --- | --- |

-- 3 会员储值：balance = Σ(amount × direction)，gift_balance = Σ(gift_amount × direction)

## 5 风险与坑清单

按"一定会踩 → 可能踩"排序：

| # | 坑 | 规避 |
| --- | --- | --- |
| 1 | 登录失败返回 HTTP 401 → 前端清登录态跳登录页 | 业务失败一律 200 + 非 0 code |
| 2 | **Pydantic v2 把 `Decimal` 序列化成字符串**，前端做运算得到 NaN | 响应模型声明 `float` 或用 `field_serializer`，阶段 0 定规范 |
| 3 | `datetime` 默认输出 ISO（带 `T`），接口约定是 `YYYY-MM-DD HH:mm:ss` | 统一序列化格式，避免前端解析失败 |
| 4 | `tinyint` 被声明成 `bool` → 输出 `true/false`，前端类型是 `number` | Pydantic 用 `int` |
| 5 | `passlib` + `bcrypt ≥ 4.0` 报 `__about__` AttributeError | 不用 passlib，直接 `bcrypt` |
| 6 | 前端只对 3 段路径注入 `request_id`，其他接口要幂等也拿不到 | 幂等只做在这三类接口上（充值需补列） |
| 7 | 单号 `MAX+1` 并发重号 | `sys_no_seq` + `LAST_INSERT_ID(expr)` |
| 8 | 86 条外键全 RESTRICT，测试数据清不掉 | fixture 用 `SET FOREIGN_KEY_CHECKS=0` + `TRUNCATE`，或按依赖逆序删 |
| 9 | 促销 `MEMBER` 重复扣减 → 顾客被多收钱 | 以 Mock 行为为准（calc 不算 MEMBER），上线前收银台实测 |
| 10 | 直接 `UPDATE inv_stock` 而不写流水 → 账实不符 | 库存变动**只走 `stock_service` 一个入口**，同时写 `inv_stock_flow` |
| 11 | 报表用商品当前进价算毛利 → 历史毛利被污染 | 一律用明细 `cost_price` 快照 |
| 12 | `/reports/sales/hourly` 不补 0 → 前端折线断裂 | 服务端补齐 24 条 |
| 13 | 分页 `total` 误返回当前页条数 | `total` = 满足条件的总记录数，`page` 从 1 起，`page_size` ≤ 100 |
| 14 | 字段名不一致（`promo_name` 写成 `label`；`product_ids` 写成 `product_id`） | 前端**不做字段映射**，名字不符 = 数据不显示/推荐永远为空 |
| 15 | 数据范围过滤写在路由层 → 越权 | 统一在 repository 注入 |
| 16 | 文件流接口包了 `ApiResult` | 导出/小票直接 `StreamingResponse` + `Content-Disposition` |
| 17 | BI 挖掘写在 `async def` 里 → 事件循环卡死、全站超时 | 丢线程/进程池；或用独立 worker 轮询任务表 |
| 18 | 多 worker 下进程内缓存不一致 | 单 worker，或只缓存低频数据 |
| 19 | 备份用 `mysqldump` 在 Windows 下的路径与密码提示问题 | 用 `--defaults-extra-file` 传凭据，避免交互式提示挂住 |
| 20 | 时区混用（DB 存本地、代码用 UTC） | 全链路 `Asia/Shanghai`（CON-07） |
| 21 | 重新生成演示账号密码哈希 → 与 `02_init_data.sql` 及文档不一致 | 直接用库里的 `$2b$` 哈希 + `checkpw` |
| 22 | 审计日志被改成可编辑 | `sys_operation_log` 只增不改（仅管理员归档） |

## 6 里程碑与优先级分批

不建议按"模块顺序"平均用力，按下面三批推进：

| 批次 | 内容 | 达成标志 |
