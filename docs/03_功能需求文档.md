## 1 引言

### 1.1 编写目的

本文档面向"基于 FastAPI 的中小型社区超市销售管理系统"（以下简称"本系统"），完整定义系统在需求分析阶段确定的功能边界、业务规则、数据约束与质量属性，作为后续概要设计、数据库设计、接口设计、编码实现与测试验收的唯一依据。

文档要达到三个目的：

1. **界定范围**：明确哪些业务做、哪些不做，防止开发过程中功能无序膨胀，也便于在论文中论证"系统边界"的合理性。
2. **可测试**：每一项功能需求均具备唯一编号、明确的输入、处理规则、输出与异常分支，可直接派生为测试用例。
3. **可追溯**：需求编号在需求→设计→代码→测试之间保持一一对应，论文中的功能实现章节可直接引用编号，形成需求追踪矩阵。

### 1.2 项目背景

社区超市是零售业态中数量最多、离居民最近的一类经营主体，通常营业面积在 100～500 平方米，经营品类集中于生鲜果蔬、粮油调味、休闲食品、日用百货等高频刚需商品。这类门店具有三个显著矛盾：

- **管理需求真实存在，但买不起也用不动 ERP**：传统商超 ERP 功能庞大、部署沉重、按年收费，对只有 3～15 名员工、一两台收银机的社区超市而言，投入产出比极低。
- **经营决策依赖经验，数据沉淀为"死账"**：绝大多数社区超市的收银机只做"收钱"，交易数据留在本地，既不能形成经营看板，也不能反哺采购与陈列决策。进货靠"拍脑袋"、库存靠"目测"，导致缺货与积压同时存在。
- **人员流动性高，培训成本敏感**：收银员多为兼职或临聘，系统必须在半小时内上手，任何需要多级菜单、复杂操作的交互都会直接拉低收银效率。

同时，本系统在技术选型上具有明确的教学与研究价值：**FastAPI** 以异步非阻塞、Pydantic 强类型校验、自动生成 OpenAPI 文档为特征，在开发效率、接口规范性与并发性能之间取得了很好的平衡；其处于 Python 生态之内，可无缝调用 pandas、mlxtend 等数据分析库，为后续接入购物篮关联分析（Apriori / FP-Growth）等智能能力预留了通道。这既贴合"轻量、快、好维护"的社区超市业务诉求，也构成了本课题"设计"层面的主要论证点。

本系统立足单店及 2～5 家小型连锁门店的经营场景，围绕"进—销—存—会—析"五个环节，构建一套部署简单、操作直观、数据闭环的销售管理系统。

### 1.4 术语与缩略语

| 术语 / 缩略语 | 全称 | 说明 |
| --- | --- | --- |
| SKU | Stock Keeping Unit | 最小库存单位。同一商品的不同规格（如 500ml / 1.5L）视为不同 SKU |
| SPU | Standard Product Unit | 标准商品单元，一组同款不同规格 SKU 的聚合概念 |
| POS | Point of Sale | 销售终端，本系统中指收银台页面及其配套硬件 |
| 进销存 | — | 采购进货、销售出货、库存结存三者的合称 |

| RBAC | Role-Based Access Control | 基于角色的访问控制模型：用户—角色—权限三级授权 |
| JWT | JSON Web Token | 无状态令牌式认证技术，由 Header、Payload、Signature 三段组成 |
| ORM | Object Relational Mapping | 对象关系映射，本系统采用 SQLAlchemy 2.0 |
| DTO | Data Transfer Object | 数据传输对象，本系统由 Pydantic 模型承担 |
| 移动加权平均 | Moving Weighted Average | 一种存货计价方法，每次入库后重算单位成本 |
| 临期商品 | Near-expiry Product | 距保质期截止日小于设定阈值（默认 30 天）的商品 |
| 客单价 | Average Transaction Value | 一定周期内销售额 ÷ 交易笔数 |
| 毛利率 | Gross Margin Rate | （销售额 − 销售成本）÷ 销售额 × 100% |
| 动销率 | Sell-through Rate | 有销售记录的商品数 ÷ 在售商品总数 × 100% |
| 关联规则 | Association Rule | 形如 A→B 的规则，表示购买 A 的顾客有较大概率同时购买 B |
| 支持度 | Support | 项集在全部交易中出现的频率 |
| 置信度 | Confidence | 在包含 A 的交易中同时包含 B 的比例 |
| 提升度 | Lift | 置信度 ÷ B 的支持度，>1 表示正相关 |
| ESC/POS | — | 小票打印机的通用指令集标准 |
| P0 / P1 / P2 | — | 需求优先级，见 1.5 节 |

## 2 项目总体描述

### 2.1 系统目标

本系统面向中小型社区超市，构建一套覆盖"商品—采购—库存—销售—会员—分析"全链路的一体化信息管理系统，具体目标如下：

| 编号 | 目标 | 可度量指标 |
| --- | --- | --- |
| G-01 | 用统一数字系统替代手工台账与纸质记录 | 商品、库存、会员、销售四类数据 100% 落库，无纸化率 ≥ 90% |
| G-02 | 提升收银效率，压缩顾客排队时长 | 单笔交易平均录入时间 ≤ 30 秒，15 件商品以内结账 ≤ 60 秒 |
| G-03 | 实现库存可视化与自动预警 | 库存账实相符率 ≥ 98%，缺货与临期商品提前 3 天预警 |
| G-04 | 沉淀会员资产，提升复购 | 会员消费占比可统计，储值/积分流水笔笔可追溯 |
| G-05 | 让经营数据可视、可用于决策 | 提供日报/月报/商品排行/毛利分析，报表生成 ≤ 3 秒 |
| G-06 | 挖掘交易数据价值，形成技术特色 | 支持基于 Apriori / FP-Growth 的商品关联分析，输出可执行的捆绑与陈列建议 |
| G-07 | 技术架构轻量、可部署、可扩展 | 单机一键部署，接口自动生成文档，新增业务模块不改动已有代码 |

### 2.2 目标用户与角色分析

系统采用 RBAC 模型，预置 5 个角色，覆盖社区超市的全部岗位。考虑到社区超市"一人多岗"的现实，允许一个用户绑定多个角色，权限取并集。

| 角色编码 | 角色名称 | 典型人员 | 核心职责 | 数据可见范围 |
| --- | --- | --- | --- | --- |
| ADMIN | 系统管理员 | 老板 / IT 兼管 | 用户、角色、权限、参数配置、备份恢复、日志审计 | 全部数据 + 系统配置 |
| MANAGER | 店长 / 经营者 | 老板本人 | 商品与价格维护、促销设置、采购审批、查看全部报表 | 本门店全部经营数据 |
| CASHIER | 收银员 | 前台店员 | 收银结算、会员办理、退货申请、交班对账 | 仅本人收银流水、会员基础信息 |
| STOCKER | 库管 / 理货员 | 后场员工 | 入库、出库、盘点、报损、临期处理 | 库存、采购收货数据 |
| PURCHASER | 采购员 | 老板或专职 | 供应商维护、采购下单、收货确认、对账 | 采购、供应商、库存数据 |
| MEMBER | 会员顾客 | 周边居民 | 出示会员码、查询积分与储值、查看消费记录 | 仅本人数据 |

**典型使用画像**：

- **王老板（45 岁，店长兼采购）**：关心"今天卖了多少、赚了多少、什么货该补了"。每日开店前看一次经营看板，每周看一次商品排行与滞销清单，据此决定进货单。对系统要求是"数据准、看得懂、别让我学"。
- **小李（19 岁，兼职收银员）**：只关心"扫码快不快、收钱对不对"。对系统要求是键盘全流程可操作、不用鼠标、出错能一键撤销。
- **张阿姨（52 岁，常客）**：关心"我卡里还有多少钱、积分能抵多少"。对系统要求是报手机号就能查、储值余额看得清。

### 2.3 中小型社区超市业务特点分析

本节是需求设计的关键前提。社区超市与大型商超、便利店在业务形态上存在显著差异，本系统的功能取舍与交互设计均由这些特点推导而来。

| 编号 | 业务特点 | 对系统的直接约束 |
| --- | --- | --- |
| C-01 | 经营面积小（100～500 ㎡），SKU 数量少而精（通常 2000～8000） | 不需要复杂的多级品类树（3 级足够）；商品列表必须支持模糊搜索而非层层点击 |
| C-02 | 人员精简（3～15 人），一人多岗 | 必须支持多角色绑定；权限粒度为"功能 + 数据范围"，不做逐按钮级过度设计 |
| C-03 | 客群固定，以周边 1 公里居民为主，复购率高 | 会员是核心资产，会员识别必须快（手机号后 4 位即可带出）；需支持储值以锁定复购 |
| C-04 | 收银高峰集中（早 7:00—9:00、晚 17:00—20:00），瞬时并发高 | 收银接口必须异步非阻塞；高峰期不得因报表统计等操作阻塞收银 |
| C-05 | 生鲜与短保商品占比高（可达 40%） | 必须支持保质期管理与临期预警；必须支持按批次/先进先出出库；报损流程要简单 |
| C-06 | 商品条码不规范，存在称重商品与散装商品 | 必须支持"无码商品"临时建档与快捷键录入；必须支持金额码/称重码解析（预留电子秤接口） |
| C-07 | 支付以移动支付为主（微信/支付宝占比可达 80% 以上） | 必须支持多种支付方式与混合支付；必须记录每种支付方式的明细金额以便对账 |
| C-08 | 进货渠道分散，常与多家批发商/农贸摊贩交易，票据不规范 | 采购环节必须"轻"：支持快速建单、支持无单直接入库、支持事后补录供应商 |
| C-09 | 门店可能不止一家（2～5 家小店），但无需集团化管控 | 必须支持多门店数据隔离与基础调拨；不需要复杂的组织架构树与结算体系 |
| C-10 | 经营者财务知识有限，不适用复杂会计科目 | 成本核算采用简单直观的移动加权平均法；报表以"钱"和"件"为单位，不用会计术语 |
| C-11 | 网络条件一般，偶有断网 | 收银端需具备弱网可用能力（本地暂存 + 恢复后补传）；核心数据操作必须事务化 |

### 2.4 系统总体功能结构

系统划分为 11 个功能模块，形成三层结构：

**第一层：基础支撑层** —— 认证与权限管理、基础数据管理、系统管理。为上层业务提供用户、权限、字典、参数、日志等公共能力。

**第二层：业务主流程层** —— 商品管理、供应商与采购管理、库存管理、销售与收银管理。构成"进—销—存"闭环，是系统的核心骨架。

**第三层：增值分析层** —— 会员管理、促销管理、统计报表、智能数据分析。沉淀会员资产、驱动营销决策、挖掘数据价值，是论文中体现设计深度与创新性的部分。

### 2.5 运行环境与技术约束

#### 2.5.1 技术选型

| 层次 | 技术 | 版本 | 选型理由 |
| --- | --- | --- | --- |
| 后端框架 | FastAPI | ≥ 0.115 | 异步高性能、依赖注入清晰、自动生成 OpenAPI 文档 |
| ASGI 服务器 | Uvicorn | ≥ 0.32 | 轻量、支持多 worker，便于单机部署 |
| 数据校验 | Pydantic | ≥ 2.9 | 强类型校验 + 序列化一体，接口契约明确 |
| ORM | SQLAlchemy | ≥ 2.0 | 支持异步会话，2.0 风格统一查询语法 |
| 数据库迁移 | Alembic | ≥ 1.13 | 版本化 DDL 管理，便于论文中展示数据库演进 |
| 数据库 | MySQL | 8.0 | 事务可靠、社区成熟、本机已部署 |

#### 2.5.3 设计约束

| 编号 | 约束 | 说明 |
| --- | --- | --- |
| CON-01 | 后端必须为 FastAPI + ASGI 异步架构 | 与论文题目一致，禁止改用同步框架 |
| CON-02 | 前后端分离，后端只提供 RESTful JSON 接口 | 前端不通过服务端模板渲染业务页面 |
| CON-03 | 所有接口必须由 Pydantic 模型显式声明入参出参 | 保证 OpenAPI 文档完整可用 |
| CON-04 | 所有数据库写操作必须置于事务中 | 保证收银、入库等多表操作的原子性 |
| CON-05 | 业务逻辑必须位于 service 层，不得堆砌在路由函数中 | 保证可测试性与可维护性 |
| CON-06 | 金额字段统一使用 DECIMAL(12,2)，禁止 float | 避免浮点误差导致对账不平 |
| CON-07 | 时间统一按门店本地时区存储与展示 | 避免跨时区聚合错位 |
| CON-08 | 单机部署，不引入微服务与消息中间件 | 与门店规模匹配，控制复杂度 |
| CON-09 | 一期不接入真实微信/支付宝支付网关，采用"支付方式登记"方式 | 商户资质限制；通过扩展点预留接入位置 |

### 2.6 设计原则

1. **够用即好（Fit for Purpose）**：功能以社区超市真实需要为界，拒绝照搬大型商超 ERP。每一个功能都必须能回答"老板会不会用、员工学不学得会"。
2. **收银优先（POS First）**：收银是整个系统的最高优先级场景，任何设计冲突都以"不拖慢收银"为裁决标准。报表、分析等重操作必须与收银链路解耦。
3. **数据一次录入，多处复用**：商品档案录入后，采购、库存、销售、报表全部复用，杜绝重复录入。
4. **不可逆操作留痕**：退货、作废、改价、盘点调整等敏感操作必须记录操作人、时间、前后值。
5. **接口即文档**：依托 FastAPI 自动生成的 Swagger / ReDoc，接口文档与代码同步演进，降低维护成本。
6. **分层解耦**：路由层（router）→ 服务层（service）→ 数据访问层（repository / ORM）→ 模型层（model），层间单向依赖，便于单元测试。

### 3.1 认证与权限管理模块（AUTH）

模块职责：解决"谁能进系统、进来能干什么、干过什么"三个问题，是全系统的安全入口。

#### 3.1.1 功能清单

| 编号 | 功能名称 | 优先级 | 简述 |
| --- | --- | --- | --- |
| FRS-AUTH-001 | 账号密码登录 | P0 | 用户名 + 密码 + 图形验证码，换取 JWT |
| FRS-AUTH-002 | 退出登录 | P0 | 客户端丢弃令牌，服务端记录登出日志 |
| FRS-AUTH-003 | 令牌刷新 | P0 | 用 refresh token 换新 access token |
| FRS-AUTH-004 | 修改本人密码 | P0 | 校验旧密码，新密码需满足强度策略 |
| FRS-AUTH-005 | 图形验证码 | P1 | 4 位字符，2 分钟有效，一次性使用 |
| FRS-AUTH-006 | 登录失败锁定 | P1 | 连续 5 次失败锁定 15 分钟 |
| FRS-AUTH-007 | 密码强度策略 | P1 | 长度 ≥ 8，含字母与数字，禁止弱口令 |
| FRS-AUTH-008 | 用户管理 | P0 | 用户增删改查、启用停用、重置密码 |
| FRS-AUTH-009 | 角色管理 | P0 | 角色增删改查，绑定权限集合 |
| FRS-AUTH-010 | 权限（菜单）管理 | P0 | 权限树维护，支持按钮级权限点 |
| FRS-AUTH-011 | 用户角色分配 | P0 | 一个用户可绑定多个角色 |
| FRS-AUTH-012 | 数据范围控制 | P1 | 按门店/本人限定可见数据 |
| FRS-AUTH-013 | 操作日志 | P0 | 记录敏感操作的人、时间、目标、前后值 |
| FRS-AUTH-014 | 登录日志 | P1 | 记录登录时间、IP、设备、结果 |
| FRS-AUTH-015 | 在线会话管理 | P2 | 查看在线用户，强制下线 |

#### 3.1.2 详细说明

**FRS-AUTH-001 账号密码登录**

- **输入**：`username`（字符串，3～20 位）、`password`（字符串，8～32 位）、`captcha_key`、`captcha_code`。
- **处理规则**：
  1. 校验验证码是否与缓存中的值一致且未过期，不一致直接返回错误；
  2. 按 `username` 查询用户，用户不存在或已停用一律返回统一提示"用户名或密码错误"（防止用户名枚举）；
  3. 使用 bcrypt 校验密码；
  4. 校验通过后查询该用户绑定的角色及角色关联的权限码集合，写入令牌载荷；
  5. 生成 access token（有效期 2 小时）与 refresh token（有效期 7 天）；
  6. 异步写入登录日志，并更新 `last_login_at`、`login_count`。
- **输出**：`{ access_token, refresh_token, token_type: "Bearer", expires_in, user_profile: { id, username, real_name, roles[], permissions[], store_id } }`
- **异常分支**：
  - 验证码错误 → 错误码 `AUTH_1001`；
  - 用户名或密码错误 → `AUTH_1002`，剩余尝试次数递减提示；
  - 账号被锁定 → `AUTH_1003`，附带解锁时间；
  - 账号已停用 → `AUTH_1004`。

**FRS-AUTH-006 登录失败锁定**

- 同一用户名连续失败 5 次，锁定 15 分钟；锁定期间即使密码正确也拒绝登录。
- 计数以"用户名 + IP"为维度，成功登录后清零，锁定结束后自动解除。
- 锁定与解锁事件均写入登录日志。

**FRS-AUTH-012 数据范围控制**

数据范围分四档，与角色绑定：

| 范围码 | 名称 | 含义 |
| --- | --- | --- |
| ALL | 全部数据 | 跨门店可见 |
| STORE | 本门店 | 仅可见所属门店数据 |
| DEPT | 本人所在岗位 | 仅可见本岗位相关单据 |
| SELF | 仅本人 | 例如收银员仅可见自己经手的交易 |

实现方式：在 service 层统一注入数据范围过滤条件，禁止在路由层手写 `where` 条件，避免遗漏导致越权。

**FRS-AUTH-013 操作日志**

以下操作强制记录日志：商品价格修改、促销规则增删改、退货、单据作废、盘点调整、库存手工调整、权限变更、数据备份与恢复、参数配置修改。

日志字段：操作人 ID、操作人姓名、模块、操作类型、目标对象类型与 ID、操作前值（JSON）、操作后值（JSON）、IP、User-Agent、操作时间、耗时毫秒、结果（成功/失败）。

- **约束**：日志表只允许插入，不提供修改与删除接口（仅管理员可归档）。

| 备注 | 文本 | 否 | ≤ 200 字符 |

- **处理规则**：
  1. 校验必填项与格式；
  2. 校验商品编码、主条码唯一性；
  3. 若填写初始库存且 > 0，调用库存服务生成期初入库单并写库存流水；
  4. 保存商品记录，返回商品 ID。
- **异常分支**：必填缺失 → `PRD_2001`；编码/条码重复 → `PRD_2002`；售价低于进价未确认 → `PRD_2003`。

**FRS-PRD-004 商品档案删除/停用**

- 判定规则：如果该商品存在采购单、销售单、库存流水、盘点单中任意一条业务记录，则**禁止物理删除**，只能执行"停用"；停用后该商品不再出现在收银台选择列表中，但历史单据仍可正常显示与统计。
- 无任何业务记录的商品允许物理删除，删除前需二次确认。
- 删除与停用操作均写入操作日志。

**FRS-PRD-007 条码管理**

- 支持一个商品绑定多个条码：主条码 1 个（唯一），附加条码 N 个（如旧包装条码、供应商条码）。
- 收银台扫码时按"任一匹配条码"定位商品；命中多个商品时（数据异常）弹出候选列表让收银员选择。
- 支持"金额码/称重码"解析：形如 `22` 开头、含商品编号与金额/重量的 13 位条码，按预设规则拆分（用于生鲜散装商品）。解析规则可配置前缀。

**FRS-PRD-008 多规格商品**

- 以 SPU 组织：SPU 记录共用属性（名称、品牌、分类），SKU 记录独立属性（规格、条码、价格、库存）。
- 新增 SKU 时可批量复制 SPU 下已有 SKU 的价格与库存参数，减少重复录入。

**FRS-PRD-012 Excel 批量导入**

- 提供标准模板下载；导入流程：上传文件 → 解析 → 逐行校验 → 返回校验报告 → 用户确认 → 落库。
- 校验规则：必填项、编码与条码唯一性、分类是否存在、单位是否存在、数值合法性、价格逻辑（售价 ≥ 进价）。
- 部分失败策略：可选择"全部回滚"或"跳过错误行导入正确行"（默认全部回滚，保证数据一致）。
- 返回报告包含：总行数、成功数、失败数、每行失败原因（行号 + 字段 + 原因）。

| FRS-PUR-002 | 供应商商品关联 | P1 | 记录某供应商可提供的商品及其供货价 |
| FRS-PUR-003 | 供货价历史 | P1 | 记录每次采购单价，形成价格趋势 |
| FRS-PUR-004 | 采购订单创建 | P0 | 手工建单或由补货建议生成 |
| FRS-PUR-005 | 采购订单审核 | P0 | 提交 → 审核通过/驳回 |
| FRS-PUR-006 | 采购订单修改与作废 | P0 | 未收货可修改，已收货不可作废 |
| FRS-PUR-007 | 收货入库 | P0 | 按单收货，支持部分收货与超收 |
| FRS-PUR-008 | 收货差异处理 | P1 | 数量/质量不符时登记差异 |
| FRS-PUR-009 | 无单快速入库 | P1 | 现场交易无需建单，直接生成入库单 |
| FRS-PUR-010 | 采购退货 | P1 | 退给供应商，减库存并冲减应付 |
| FRS-PUR-011 | 采购订单查询 | P0 | 多条件查询、状态过滤、导出 |
| FRS-PUR-012 | 供应商对账 | P1 | 按周期汇总采购、退货、已付、未付 |
| FRS-PUR-013 | 付款登记 | P1 | 登记实际付款，更新应付余额 |
| FRS-PUR-014 | 采购统计 | P1 | 按供应商/商品/时段统计采购金额与数量 |

#### 3.4.2 详细说明

**FRS-PUR-004 采购订单创建**

- **输入**：供应商、预计到货日期、商品明细行（商品、数量、单价、备注）、整单备注。
- **处理规则**：
  1. 生成采购单号，格式 `CG` + `yyyyMMdd` + 4 位流水（如 `CG202609150003`），流水号由数据库序列或加锁计数生成，防止并发重号；
  2. 校验商品是否存在且启用；
  3. 计算每行金额 `数量 × 单价`，汇总整单金额 `total_amount`；
  4. 状态置为"待审核"；
  5. 若来源为补货建议，记录来源标识便于追溯。
- **输出**：采购单 ID 与单号。
- **异常分支**：供应商已停用 → `PUR_3001`；明细为空 → `PUR_3002`；商品不存在 → `PUR_3003`；数量或单价 ≤ 0 → `PUR_3004`。

**FRS-PUR-005 采购订单审核**

- 单据状态机：`待审核 → 已审核 → 部分收货 → 已收货 → 已完成`；任一非终态可 `已作废`。
- 审核操作需 MANAGER 及以上权限。
- 驳回时必须填写驳回原因，单据状态回退为"待修改"。
- 状态变更写入操作日志。

**FRS-PUR-007 收货入库**

- **处理规则**：
  1. 只能对"已审核"或"部分收货"状态的采购单收货；
  2. 本次收货数量 ≤ 订单数量 − 已收数量（超收需开启"允许超收"参数并填原因）；
  3. 生成采购入库单，逐行写入库存流水（`+数量`），更新实时库存；
  4. 重算商品移动加权平均成本：

     `新成本 = (原库存数量 × 原成本 + 本次入库数量 × 本次进价) ÷ (原库存数量 + 本次入库数量)`

  5. 若商品为保质期商品，生成批次记录（批次号、生产日期、到期日期）；
  6. 更新采购单累计收货数量与状态；
  7. 同步更新该商品的"最近进价"与供货价历史。
- **事务要求**：入库单、库存、流水、成本、批次、采购单状态更新必须在同一事务内，任一失败全部回滚。
- **异常分支**：单据状态不允许收货 → `PUR_4001`；收货数量超限 → `PUR_4002`。

**FRS-PUR-009 无单快速入库**

针对社区超市常见的"批发商送货上门，无正式订单"场景：

- 收银/库管在 1 个页面内完成：选择或快速新建供应商 → 扫码/搜索添加商品 → 填数量与单价 → 提交。
- 提交后直接生成"已完成"状态的采购单与入库单，库存即时增加、成本即时重算。
- 单据标记来源为"无单入库"，便于事后统计。

**FRS-PUR-012 供应商对账**

- 输入：供应商、起止日期。
- 汇总逻辑：
  - 期初应付 = 上期期末应付；
  - 本期增加 = 本期采购入库金额合计（含退货冲减）；
  - 本期减少 = 本期付款登记金额合计；
  - 期末应付 = 期初应付 + 本期增加 − 本期减少。
- 输出：对账单（可按明细展开），支持导出 Excel 发送给供应商核对。

### 3.5 库存管理模块（INV）

模块职责：这是全系统数据准确性的核心。库存模块以"流水驱动"为原则——**任何库存变化必须由单据产生，禁止直接改库存数字**。

#### 3.5.1 功能清单

| 编号 | 功能名称 | 优先级 | 简述 |
| --- | --- | --- | --- |
| FRS-INV-001 | 实时库存查询 | P0 | 按商品/分类查询各门店库存 |
| FRS-INV-002 | 库存流水台账 | P0 | 每一笔出入库的完整记录 |
| FRS-INV-003 | 入库管理 | P0 | 采购入库、退货入库、调拨入库、其他入库 |
| FRS-INV-004 | 出库管理 | P0 | 销售出库、报损、领用、调拨出库 |
| FRS-INV-005 | 库存盘点 | P0 | 全盘/抽盘，生成盘点单与差异 |
| FRS-INV-006 | 盘点差异调整 | P0 | 审核后自动生成调整流水 |
| FRS-INV-007 | 库存预警 | P1 | 低于安全库存、超过上限、临期三类预警 |
| FRS-INV-008 | 成本核算 | P0 | 移动加权平均，记录每笔出库成本 |
| FRS-INV-009 | 批次与保质期 | P1 | 批次入库、先进先出出库、临期拣选 |

| FRS-INV-012 | 库存流水查询与导出 | P1 | 按商品/单据类型/时段查询导出 |
| FRS-INV-013 | 库存周转分析 | P2 | 周转天数、周转率 |
| FRS-INV-014 | 库存金额统计 | P1 | 按成本价与售价双口径统计库存金额 |

#### 3.5.2 详细说明

**FRS-INV-001 实时库存查询**

- 展示字段：商品编码、名称、规格、单位、当前库存数量、安全库存、库存状态（正常/预警/超储）、成本单价、库存金额（成本口径）、库存金额（售价口径）、最近入库时间、最近出库时间。
- 支持按分类、供应商、库存状态、关键字筛选，支持库存数量升序排序（便于快速找缺货品）。
- 性能要求：单门店 8000 SKU 全量分页查询响应 ≤ 800ms。

**FRS-INV-005 库存盘点**

- **盘点流程**：创建盘点单（选择范围：全盘 / 按分类 / 按货架 / 指定商品）→ 系统冻结该范围账面库存快照 → 录入实盘数量 → 生成差异 → 提交审核 → 审核通过后生成调整流水。
- **差异判定**：
  - `差异数量 = 实盘数量 − 账面数量`；
  - 差异 ≠ 0 的行必须填写原因（漏记、损耗、错盘、串码等）；
  - 差异率 = |差异数量| ÷ 账面数量，超过阈值（默认 5%）的行需店长复核。
- **调整规则**：审核通过后，对每个差异行生成一条库存流水，单据类型为"盘点调整"，方向由差异正负决定；同时按当前成本价计算损益金额并记入盘点损益。
- **约束**：盘点单创建后，该范围内的商品在盘点期间仍可正常销售，但销售流水会作为"盘点期间变动"单独列出，避免把销售造成的差异误判为盘亏。
- **异常分支**：存在未填原因的差异行不允许提交 → `INV_5001`；盘点单已审核不允许重复调整 → `INV_5002`。

**FRS-INV-007 库存预警**

三类预警，由定时任务每日 07:00 与每次库存变动后增量计算：

| 预警类型 | 触发条件 | 提示方式 | 建议动作 |
| --- | --- | --- | --- |
| 缺货预警 | 库存数量 ≤ 安全库存下限 | 首页红色标记 + 待办数量 | 生成补货建议 |
| 超储预警 | 库存数量 ≥ 库存上限 | 首页橙色标记 | 暂停采购、考虑促销 |
| 临期预警 | 保质期商品，剩余天数 ≤ 临期阈值 | 首页黄色标记 + 明细清单 | 折价促销或报损 |
| 零动销预警 | 连续 30 天无销售记录且库存 > 0 | 周报中列出 | 下架或清仓 |

**FRS-INV-008 成本核算**

- 采用移动加权平均法。商品表冗余存储 `avg_cost` 字段，每次入库后立即重算。
- 销售出库时，按出库瞬间的 `avg_cost` 计算销售成本并写入销售明细，保证历史毛利数据不会因后续进货价变动而失真。
- 支持"成本重算"工具：当发生历史单据补录后，可对指定商品或时段重算成本并修正毛利（需管理员权限，记录日志）。

**FRS-INV-009 批次与保质期**

- 保质期商品入库时生成批次：批次号 = `商品编码` + `-` + `yyyyMMdd` + `-` + 2 位流水。
- 出库策略：默认先进先出（按到期日升序拣选），生鲜类可切换为"最快到期优先"。
- 收银售出保质期商品时，可选的"批次提示"功能会在收银界面显示所售批次的到期日，帮助员工优先售出临期品。

### 3.6 销售与收银管理模块（SAL）

模块职责：系统的价值出口，也是性能与体验要求最高的模块。收银台页面的设计原则是**全程可用键盘完成，不用鼠标**。

#### 3.6.2 详细说明

**FRS-SAL-001 收银开单**

- **输入方式**：
  1. 扫码枪输入条码（HID 键盘模拟，回车结束）；
  2. 关键字模糊搜索（支持拼音首字母，如 `kqs` 匹配"可口可乐"）；
  3. 分类快捷区点击（生鲜、烟酒、饮料等）。
- **处理规则**：
  1. 按条码/关键字定位商品，校验商品已启用且允许销售；
  2. 若已在明细中，则数量 +1（称重商品不可累加）；
  3. 否则新增明细行，取价顺序为：**促销价 > 会员价（已识别会员时）> 零售价**；
  4. 记录商品快照（名称、规格、单位、单价、成本价），避免商品改名后历史单据显示错乱；
  5. 实时重算小计、优惠、应收金额；
  6. 若该商品存在关联推荐规则且购物车中有对应商品，在界面侧边显示推荐提示（见 FRS-BI-002）。
- **性能要求**：扫码到明细行渲染完成 ≤ 300ms（本地前端渲染），服务端参与的计算（如需查促销）≤ 200ms。
- **异常分支**：条码未匹配 → `SAL_6001`，界面提示"未找到商品，是否快速建档？"；商品已停用 → `SAL_6002`；库存不足（允许负库存时仅警告）→ `SAL_6003`。

**FRS-SAL-006 促销自动计算**

- 计算顺序（优先级从高到低）：商品特价 → 商品折扣 → 组合套餐 → 满减 → 满赠 → 优惠券 → 会员折扣。
- 互斥规则：同一商品的特价与折扣互斥，取优惠力度更大者；整单级促销（满减、优惠券）可与商品级促销叠加，但整单总优惠不得超过商品总金额的指定比例（默认 80%，可配置）。
- 每次优惠计算需在销售明细中记录"优惠来源"（哪个促销规则、优惠金额），便于事后核对与促销效果分析。

**FRS-SAL-009 挂单与取单**

- 挂单：将当前购物车以 JSON 快照存入挂单表，记录挂单号（当日序号）、挂单时间、操作人。
- 取单：列表展示本收银台未取挂单，点击恢复至购物车。
- 约束：挂单不占用库存、不生成收入；挂单超过 24 小时自动清理并记录；同一收银台挂单数量上限 20 单。

**FRS-SAL-010 结算收银**

- **支付方式**：现金、微信、支付宝、银行卡、会员储值、积分抵扣、其他。
- **混合支付规则**：允许多种支付方式组合，各方式金额之和必须等于应收金额；储值支付优先扣减（若勾选"优先储值"）。
- **处理流程（单事务）**：
  1. 校验购物车非空、金额一致；
  2. 生成销售单号 `XS` + `yyyyMMdd` + 4 位流水；
  3. 写入销售主单（收银员、门店、收银台、会员、应收、实收、优惠、成本合计、毛利）；
  4. 写入销售明细行（商品、数量、单价、优惠、成本、金额）；
  5. 写入支付明细行（支付方式、金额、流水号、时间）；
  6. 逐行扣减库存并写库存流水（销售出库），调用成本核算写入成本；
  7. 若为会员消费：累加消费金额、按比例增加积分、写积分流水、更新会员等级；
  8. 若使用积分抵扣：扣减积分并写积分流水；
  9. 若使用储值：扣减储值余额并写储值流水；
  10. 更新交班汇总（销售额、笔数、各支付方式金额）；
  11. 提交事务。
- **输出**：销售单号、找零金额、打印数据包。
- **异常分支**：金额不一致 → `SAL_7001`；储值余额不足 → `SAL_7002`；积分不足 → `SAL_7003`；库存不足且禁止负库存 → `SAL_7004`；事务失败 → 全量回滚并提示重试。
- **幂等性要求**：结算接口必须支持幂等键（前端生成 `request_id`），防止网络重试导致重复扣款。

**FRS-SAL-013 小票打印**

- 采用 ESC/POS 指令集，支持 58mm / 80mm 两种纸宽。
- 小票内容：门店抬头、销售单号、收银员、时间、商品明细（名称、数量、单价、金额）、优惠合计、应收、各支付方式金额、找零、会员信息（余额/本次积分）、二维码（可选，用于电子小票）、底部问候语。
- 支持"重新打印"（记录打印次数，防止重复打印用于欺诈）。
- 打印机异常时不得阻塞结算，改为异步重试或提示手工补打。

**FRS-SAL-016 销售退货**

- **输入**：原销售单号（或扫码定位）、退货明细行（商品、数量）、退款方式、退货原因。
- **校验规则**：
  1. 原单必须存在且状态为"已完成"；
  2. 退货数量 ≤ 原单数量 − 已退数量；
  3. 退货期限：默认 7 天内（可配置）；
  4. 生鲜类商品可配置"不支持退货"。
- **处理流程**：
  1. 生成退货单号 `TH` + `yyyyMMdd` + 4 位流水；
  2. 写入退货主单与明细（记录原单号与退货原因）；
  3. 库存回滚（写退货入库流水），成本按原销售成本回冲，保证毛利修正准确；
  4. 写退款记录（退款方式、金额、操作人、状态：已退款/退款失败）；
  5. 会员订单同步回退积分与消费金额；
  6. 记录操作日志（强制）。
- **异常分支**：超出退货期限 → `SAL_8001`；退货数量超限 → `SAL_8002`；原单不存在 → `SAL_8003`。
- **约束**：退货必须生成独立单据，禁止直接修改原销售单。

**FRS-SAL-018 交班与日结**

- **开钱箱**：收银员开班时登记备用金金额。
- **交班**：
  1. 汇总本班次：销售笔数、销售金额、各支付方式金额、退货金额、作废金额；
  2. 收银员输入实际现金金额，系统计算现金差异 `实际现金 − 备用金 − 现金收入 + 现金退款`；
  3. 差异 ≠ 0 时必须填写说明；
  4. 生成交班单，状态"待审核"，店长审核后归档；
  5. 交班后该收银员不再允许操作原班次单据。
- **日结**：每日营业结束后，由店长执行日结，锁定当日数据（锁定后当日单据不再允许修改与作废），生成日结报表并归档。

**FRS-MEM-006 储值充值**

- **输入**：会员、充值金额、支付方式、是否赠送及赠送金额。
- **处理规则**：
  1. 金额必须 > 0；
  2. 赠送金额按充值活动规则自动计算或手工输入（需权限）；
  3. 写入充值单与储值流水（类型：充值 + / 赠送 +）；
  4. 更新会员 `balance` 与 `gift_balance`；
  5. 写入操作日志（涉及资金）。
- **储值分层**：本金余额 `balance` 与赠送余额 `gift_balance` 分开记录。消费时优先扣赠送余额（可配置），退款时只退本金部分，避免"充值—退款"套取赠送金额。
- **异常分支**：金额非法 → `MEM_9002`；赠送比例超限 → `MEM_9003`。

**FRS-MEM-008 会员消费档案**

展示内容：累计消费金额、累计消费笔数、客单价、最近消费时间、消费频次（月均笔数）、偏好品类 TOP5（按消费金额占比）、常购商品 TOP10。

- 支持导出与打印。

- 计算口径：

- 约束：报表金额与销售单、库存流水三方必须可对账（提供对账校验入口，勾稽不上则醒目提示）。

- 该表是库存准确性的核心校验工具，必须支持导出后与实盘核对。

### 3.10 智能数据分析模块（BI）

模块职责：挖掘交易数据中的商品关联关系，输出可执行的经营建议。这是本系统区别于普通收银软件的核心差异点，也是论文中体现技术深度与创新性的部分。

#### 3.10.1 功能清单

| 编号 | 功能名称 | 优先级 | 简述 |
| --- | --- | --- | --- |
| FRS-BI-001 | 购物篮数据准备 | P1 | 从销售单抽取交易事务集，支持清洗与过滤 |
| FRS-BI-002 | 关联规则挖掘 | P1 | 基于 Apriori / FP-Growth 挖掘频繁项集与规则 |
| FRS-BI-003 | 挖掘参数配置 | P1 | 最小支持度、最小置信度、最小提升度可调 |
| FRS-BI-004 | 关联规则结果展示 | P1 | 规则列表、指标可视化、排序筛选 |
| FRS-BI-005 | 商品关联推荐 | P1 | 收银台实时推荐搭配商品 |
| FRS-BI-006 | 捆绑销售建议 | P2 | 基于强关联规则生成捆绑套餐建议 |
| FRS-BI-007 | 交叉陈列建议 | P2 | 基于关联强度输出货架相邻摆放建议 |
| FRS-BI-008 | 销售趋势预测 | P2 | 基于移动平均/指数平滑预测短期销量 |
| FRS-BI-009 | 智能补货建议 | P2 | 结合销量、库存、在途量生成补货清单 |
| FRS-BI-010 | 算法性能对比 | P2 | Apriori 与 FP-Growth 在同一数据集上的耗时对比 |
| FRS-BI-011 | 分析任务调度 | P2 | 定时（如每日凌晨）自动重跑分析 |
| FRS-BI-012 | 分析结果导出 | P2 | 规则与建议导出 Excel |

#### 3.10.2 详细说明

**FRS-BI-001 购物篮数据准备**

- **数据来源**：销售主单 + 销售明细，按 `销售单号` 聚合成"事务"——同一笔交易中出现的所有商品构成一个项集。
- **抽取规则**：
  1. 排除退货单与作废单；
  2. 排除赠品行（金额为 0）；
  3. 只保留商品粒度（同一商品多次出现合并为一项）；
  4. 可配置时间窗口（默认近 90 天）；
  5. 可过滤低频商品（出现次数少于 N 次的商品不参与挖掘，减少噪声）。
- **输出**：事务列表（每行一笔交易的商品编码集合）与商品编码到名称的映射表。
- **实现要点**：使用 SQL 聚合与 pandas 完成，避免在 Python 层做逐单循环。

**FRS-BI-002 关联规则挖掘**

- **算法**：同时实现 Apriori 与 FP-Growth（依托 `mlxtend.frequent_patterns`），用于对比。
- **输入参数**：

| 参数 | 说明 | 默认值 |
| --- | --- | --- |
| `min_support` | 最小支持度 | 0.01（即 1% 的交易）|
| `min_confidence` | 最小置信度 | 0.3 |
| `min_lift` | 最小提升度 | 1.0 |
| `max_len` | 最大项集长度 | 3 |
| `date_range` | 数据时间窗口 | 近 90 天 |
| `min_item_count` | 商品最低出现频次 | 5 |

- **处理流程**：
  1. 加载事务集，构造 one-hot 编码矩阵；
  2. 调用算法挖掘频繁项集，输出支持度；
  3. 由频繁项集生成关联规则，计算置信度与提升度；
  4. 按提升度降序、置信度次之排序；
  5. 过滤掉提升度 ≤ 1 的无意义规则；
  6. 将结果写入关联规则表，记录本次任务参数与执行耗时，便于对比。
- **输出**：规则集合，每条规则包含：前件项集、后件项集、支持度、置信度、提升度、杠杆率、确信度。
- **性能约束**：在 5 万笔交易、3000 个 SKU、`min_support = 0.01` 的条件下，单次挖掘 ≤ 60 秒（异步任务执行，前端轮询进度）。
- **异常分支**：交易数据不足（< 100 笔）→ `BI_10001`；参数非法（支持度 ≤ 0 或 > 1）→ `BI_10002`；内存不足 → 建议提高支持度后重试。

**FRS-BI-004 关联规则结果展示**

- **规则列表**：`{啤酒, 尿布} → {薯片}`，并展示支持度、置信度、提升度。
- **可视化**：
  1. 支持度—置信度散点图，气泡大小表示提升度，便于快速定位"高价值规则"；
  2. 商品关联网络图（节点为商品，边权为提升度），直观展示关联簇；
  3. 关联热度矩阵（TOP 20 商品的共现频次热力图）。
- **筛选与排序**：按提升度、置信度、支持度排序；按商品、分类过滤。
- **业务解读**：每条规则附带一段自动生成的业务说明文字，例如：

  > 「购买 啤酒 的顾客中，有 62% 同时购买了 花生米。相比随机购买，这种搭配的可能性高出 3.4 倍。建议将两者相邻陈列，或设置为组合优惠。」

  这一设计的意义在于：**让不懂算法的店主也能看懂并直接采纳结论**，是答辩时可重点展示的亮点。

**FRS-BI-005 商品关联推荐**

- **触发时机**：收银台购物车发生变化时（商品加入后 300ms 防抖）。
- **推荐逻辑**：
  1. 取购物车中商品集合；
  2. 在关联规则表中查找前件被购物车包含的规则；
  3. 按提升度 × 置信度加权排序，取 TOP 3；
  4. 排除已在购物车中的商品；
  5. 返回商品名称与推荐理由（如"常与啤酒一起购买"）。
- **界面呈现**：收银界面右侧显示推荐商品小卡，点击即加入购物车，一键完成搭配销售。
- **性能要求**：推荐接口响应 ≤ 100ms（规则表走内存缓存 + 索引）。
- **降级策略**：无匹配规则或规则表为空时，静默不显示推荐区，不得影响收银。

**FRS-BI-008 销售趋势预测 / FRS-BI-009 智能补货建议**

- 趋势预测：对指定商品的历史日销量序列，采用移动平均（7 日/14 日）与一次指数平滑法预测未来 7 天销量；输出预测曲线与置信区间。
- 补货建议：`建议补货量 = 预测周期销量 + 安全库存 − 当前库存 − 在途量`，结果向下取整并考虑最小起订量。
- 输出补货清单，支持一键转为采购订单（对接 FRS-PUR-004）。

**FRS-BI-010 算法性能对比**

- 在同一事务集上分别运行 Apriori 与 FP-Growth，记录：耗时、生成频繁项集数量、内存占用（估算）。
- 结果以表格 + 柱状图呈现，并给出结论性说明（如"在支持度 0.01 时，FP-Growth 比 Apriori 快 X 倍"）。
- **该功能直接服务于论文的实验与结论章节**，是本系统在"设计"之外补充"研究"成分的关键。

**FRS-SYS-009 健康检查接口**

- `GET /api/v1/health`，返回：服务状态、数据库连通性、当前时间、版本号、运行时长。
- 要求不依赖认证、响应 ≤ 50ms，供容器探活与运维监控使用。

## 4 数据需求

### 4.1 数据实体关系概览

系统数据可分为四个域：

```
 ┌─── 主数据域 ────┐     ┌─── 业务单据域 ──────────┐
 │ 门店 / 收银台    │     │ 采购单 → 收货单 → 入库单 │
 │ 商品分类 / 商品  │◄────┤ 销售单 → 退货单          │
 │ 条码 / 规格      │     │ 盘点单 / 报损单 / 调拨单 │
 │ 供应商 / 会员    │     │ 交班单 / 充值单          │
 │ 计量单位 / 字典  │     └──────────┬──────────────┘
 └─────────────────┘                │ 单据驱动库存变动
 ┌─── 库存域 ──────┐                ▼
 │ 实时库存         │◄────── 库存流水（唯一真相源）
 │ 批次 / 成本      │                │
 └─────────────────┘                ▼
 ┌─── 权限与日志域 ─┐        ┌─── 分析域 ─────────┐
 │ 用户/角色/权限   │        │ 关联规则 / 推荐缓存 │
 │ 操作日志/登录日志│        │ 统计聚合表          │
 └─────────────────┘        └────────────────────┘
```

**核心设计原则**：`库存流水表` 是全系统库存数据的唯一真相源，`实时库存表` 是它的事务化冗余快照，两者必须时刻一致（每次变动同事务更新），以此保证可对账、可追溯。

### 4.3 关键数据约束

| 编号 | 约束 | 说明 |
| --- | --- | --- |
| DC-01 | 金额字段统一 `DECIMAL(12,2)` | 禁止使用 FLOAT / DOUBLE |
| DC-02 | 数量字段统一 `DECIMAL(12,3)` | 支持称重商品的克/千克小数 |
| DC-03 | 所有单据表必须有唯一单号 + 唯一索引 | 单号生成需并发安全 |
| DC-04 | 库存表对 `(store_id, product_id)` 建唯一索引 | 防止同一商品在同一门店出现多行库存 |
| DC-05 | 销售主单对 `request_id` 建唯一索引 | 保证结算幂等，防重复扣款 |
| DC-06 | 全部表包含 `created_at`、`updated_at` | 便于审计与数据同步 |
| DC-07 | 业务表使用逻辑删除或状态字段 | 除无业务引用的主数据外，禁止物理删除 |
| DC-08 | 外键字段建索引 | 特别关注 `product_id`、`trade_id`、`member_id`、`created_at` |
| DC-09 | 字符集统一 `utf8mb4`、排序规则 `utf8mb4_general_ci` | 支持 emoji 与中文 |
| DC-10 | 流水类表按月分区或定期归档 | 防止 `inv_stock_flow`、`sal_trade_item` 无限膨胀 |

系统采用前后端分离架构，前端为单页应用（SPA），共设计以下界面区域：

| 收银台 | 商品录入区 + 明细区 + 结算区 | **全键盘可操作**，字体大、对比度高，适配 1024×768 |
| 商品管理 | 列表 + 表单弹窗 | 支持批量操作与导入导出 |
| 库存管理 | 库存列表 + 流水 + 盘点 | 预警信息高亮 |
| 采购管理 | 订单列表 + 建单 + 收货 | 建单支持快速扫码录入 |
| 会员管理 | 会员列表 + 详情 + 充值 | 查询快，储值/积分一目了然 |
| 报表中心 | 看板 + 各类报表 | 图表为主，支持导出 |
| 智能分析 | 规则列表 + 可视化 | 结论用中文业务语言表达 |
| 系统设置 | 用户/角色/权限/参数/日志 | 权限树勾选式配置 |

**交互通用要求**：

1. 所有列表支持分页、排序、条件筛选，筛选条件可重置；

5. 收银台页面禁用浏览器刷新/后退的误触影响，网络异常时给出显式提示。

**性能保障策略**：

1. 收银核心链路使用异步数据库会话，避免阻塞；
2. 看板、报表、关联推荐结果采用"预聚合 + 缓存"策略，由 APScheduler 在营业低谷期计算；
3. 报表查询建立组合索引：`(store_id, created_at)`、`(product_id, created_at)`；
4. 关联分析作为后台任务执行，前端轮询任务状态，不占用请求线程。
