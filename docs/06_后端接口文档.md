## 1 通用约定

### 1.1 基础信息

| 项 | 约定 |
| --- | --- |
| 接口前缀 | `/api/v1` |
| 请求方法 | `GET` / `POST` / `PUT` / `DELETE` |
| 请求体格式 | `application/json; charset=utf-8`（文件上传为 `multipart/form-data`） |
| 字符编码 | UTF-8 |
| 鉴权方式 | HTTP Header `Authorization: Bearer <access_token>` |
| 时间格式 | `YYYY-MM-DD HH:mm:ss`（日期单独出现时为 `YYYY-MM-DD`） |
| 金额类型 | `DECIMAL(12,2)`，接口中为 `number`，单位元 |
| 数量类型 | `DECIMAL(12,3)`，接口中为 `number`，支持称重商品小数 |
| 布尔语义 | 后端 `tinyint`，`0` = 否 / 停用，`1` = 是 / 启用（接口中为 `number`） |
| 超时 | 前端 Axios 超时 20 秒 |

### 1.2 认证机制

采用 **JWT 双令牌**方案：

1. **登录**：`POST /auth/login`，校验图形验证码后返回 `access_token` + `refresh_token`。
2. **携带**：后续所有请求在 Header 中带 `Authorization: Bearer <access_token>`。
3. **过期**：`access_token` 过期返回 HTTP 401，前端清除登录态并跳转登录页。
4. **刷新**：`POST /auth/refresh` 用 `refresh_token` 换取新的 `access_token`。
5. **登出**：`POST /auth/logout`，服务端可将令牌加入黑名单。

**失败锁定**（对应 FRS-AUTH-006）：同一账号连续登录失败达到阈值（默认 5 次）后锁定，锁定期间返回错误码 `1003`。

### 1.3 统一响应体

**所有**接口（除文件流导出）均返回下列结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "9f2c1e4a-3b5d-4a7e-8c1f-2d6b0a9e7f31",
  "timestamp": "2026-09-15 18:30:00"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | number | 业务状态码。**`0` 表示成功**，非 0 为业务错误 |
| `message` | string | 提示信息，成功时为 `success` |
| `data` | any | 业务数据。无返回内容时为 `null` |
| `request_id` | string | 请求唯一标识，用于日志追踪 |
| `timestamp` | string | 服务端处理时间 |

> **实现要点**：`code` 为 0 时前端直接取 `data`；非 0 时前端按错误码弹提示并 reject。
> 因此**不要用 HTTP 状态码表达业务错误**——业务错误一律 HTTP 200 + 非 0 `code`，
> HTTP 状态码只用于表达传输层与认证层错误（401 / 403 / 404 / 500）。

### 1.6 幂等约定

**资金类接口必须支持幂等**（对应 FRS-SAL-010，防止网络重试导致重复扣款）。

前端会对下列路径的 `POST` 请求**自动注入** `request_id` 字段：

- `/sales/trades`（结算收银）
- `/sales/trades/...`（销售单相关操作）
- `/members/recharge`（会员充值）

后端要求：

1. 以 `request_id` 建唯一索引；
2. 若相同 `request_id` 重复到达，**不再执行**，直接返回首次的处理结果；
3. `request_id` 由前端生成（时间戳 + 随机串），也可由后端在响应中回写。

### 1.7 权限模型

**RBAC 三级授权**（对应 FRS-AUTH-009 ~ 011）：

1. **菜单级**：登录后 `/auth/me` 返回 `permissions` 权限码数组，前端据此过滤路由表；无权限的路由**不注册**，直接输入 URL 也是 404。
2. **按钮级**：后端仍需在**每个写接口**上校验权限码，前端 `v-permission` 只是体验优化。
3. **数据级**：按角色 `data_scope` 过滤数据范围：`ALL` 全部门店 / `STORE` 本门店 / `DEPT` 本岗位 / `SELF` 仅本人。

| 项 | 内容 |

**请求 Body**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |

| `items[].product_id` | number | 是 | 商品 ID |
| `items[].receive_qty` | number | 是 | 本次收货数量 |
| `items[].unit_price` | number | 是 | 实际进货单价（可与订单价不同） |
| `items[].production_date` | string | 否 | 生产日期（保质期商品） |

**业务规则（FRS-PUR-007 / 008）**

1. 支持**部分收货**：累加 `received_qty`，全部收完则订单转 `FINISHED`，否则 `PARTIAL`。

4. 收货后必须：① 增加 `inv_stock`；② 写 `inv_stock_flow`；③ **重算移动加权平均成本**。

> **移动加权平均公式**：
> `新成本 = (原库存 × 原成本 + 本次入库数量 × 本次单价) ÷ (原库存 + 本次入库数量)`

#### 3.5.3 结算收银（幂等）

| 项 | 内容 |
| --- | --- |
| 路径 | `POST /sales/trades` |
| 幂等 | **是**（`request_id` 唯一索引） |
| 性能 | P95 ≤ 500ms |

**请求 Body**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `request_id` | string | 是 | 幂等键（前端自动注入） |
| `member_id` | number | 否 | 会员 ID |
| `items` | CartItem[] | 是 | 商品明细 |
| `payments` | array | 是 | 支付明细，支持混合支付 |
| `payments[].pay_method` | string | 是 | `CASH` / `WECHAT` / `ALIPAY` / `CARD` / `BALANCE` |
| `payments[].amount` | number | 是 | 该方式支付金额 |
| `use_points` | number | 否 | 使用的积分数量 |
| `round_amount` | number | 否 | 抹零金额 |
| `remark` | string | 否 | 备注 |

**响应 `data`**：至少返回 `{ id, trade_no, receivable, received, change_amount, trade_time }`

**业务规则（结算事务，必须原子）**

1. 校验 `request_id`：已存在则**直接返回首次结果**，不重复执行。
2. 校验支付总额 = 应收金额，否则返回 `7001`。
3. 校验库存充足，否则返回 `7004`。
4. 会员余额支付时校验余额，不足返回 `7002`；积分不足返回 `7003`。
5. **同一事务内**依次完成：
   - 写 `sal_trade` 主表 + `sal_trade_item` 明细（**冗余商品名、规格、成本价快照**）
   - 写 `sal_trade_payment` 支付明细
   - 扣减 `inv_stock` 并写 `inv_stock_flow`（`flow_type=SALE_OUT`）
   - 扣减会员余额 / 增加消费积分（写 `mem_balance_flow` / `mem_point_flow`）
   - 累计 `mem_member.total_consume` / `consume_count`，触发等级升级判断
   - 更新促销统计字段（`trigger_count` / `discount_total`）
6. 生成单号 `XS + yyyyMMdd + 4 位序号`。

> **成本快照很重要**：明细里存的 `cost_price` 是成交时的成本，后续进价波动不影响历史毛利。
> 支付方式为 `BALANCE` 时，**优先扣赠送余额再扣本金余额**。

| `diff_remark` | string | 条件必填 | **现金差异不为 0 时必填**，否则前端拦截 |

**响应**：`SaleSession`（更新后的班次，含 `cash_diff`）

**业务规则**

1. `cash_diff = actual_cash − (init_cash + cash_amount)`；
2. `cash_diff ≠ 0` 且 `diff_remark` 为空 → 前端拦截（后端也应校验）；
3. 交班后本班次单据不可修改，班次状态置 `CLOSED`（待店长审核）。

#### 3.9.5 商品关联推荐（收银台实时调用）

| 项 | 内容 |
| --- | --- |
| 路径 | `POST /bi/recommend` |
| 请求 | `{ "product_ids": [17, 14] }`（**购物车中全部商品 ID 的数组**） |
| 响应 | `RecommendItem[]`（最多 4 条，按 `score` 降序） |

**错误注意**：请求字段名是 **`product_ids`（复数，数组）**，不是 `product_id`。

**推荐逻辑**

1. 遍历关联规则，找出**前件与购物车有交集**的规则；
2. 后件商品若**已在购物车中则跳过**（不推荐已买的）；
3. 同一商品命中多条规则时取 `score` 最高的一条；
4. `score = lift × confidence`；
5. `reason` 生成文案，如 `常与「青岛啤酒」一起购买`。

#### 4.3.2 统一响应体

```python
from typing import Any, Generic, TypeVar
from pydantic import BaseModel
from datetime import datetime

T = TypeVar("T")

class ApiResult(BaseModel, Generic[T]):
    code: int = 0
    message: str = "success"
    data: T | None = None
    request_id: str | None = None
    timestamp: str = ""

    @classmethod
    def ok(cls, data: Any = None) -> "ApiResult":
        return cls(code=0, message="success", data=data,
                   timestamp=datetime.now().strftime("%Y-%m-%d %H:%M:%S"))
```

> **关键**：业务错误也必须返回 HTTP 200 + 非 0 `code`，
> 只有认证失败（401）、无权限（403）、接口不存在（404）、服务端异常（500）才用 HTTP 错误码。

#### 4.3.3 鉴权依赖

```python
from fastapi import Depends, HTTPException, Header

async def get_current_user(authorization: str = Header(...)):
    """从 Authorization: Bearer <token> 解析当前用户"""
    if not authorization.startswith("Bearer "):
        raise HTTPException(status_code=401, detail="未登录")
    token = authorization[7:]
    payload = decode_jwt(token)          # 校验签名与过期时间
    if not payload:
        raise HTTPException(status_code=401, detail="登录状态已失效")
    return payload

def require_perm(*perm_codes: str):
    """权限校验依赖：@router.get('/products', dependencies=[Depends(require_perm('goods:product:list'))])"""
    async def checker(user = Depends(get_current_user)):
        if not set(perm_codes) & set(user.get("permissions", [])):
            raise HTTPException(status_code=403, detail="没有该操作的权限")
        return user
    return checker
```

#### 4.3.5 幂等实现

```python
async def check_idempotent(db, request_id: str, model) -> Any | None:
    """资金类接口幂等：request_id 已存在则直接返回首次结果"""
    if not request_id:
        return None
    exist = db.query(model).filter(model.request_id == request_id).first()
    if exist:
        return build_response_from(exist)   # 不重复执行
    return None
```

> `sal_trade.request_id` 与 `mem_balance_flow.request_id` 需建**唯一索引**，
> 并发场景下依赖数据库唯一约束兜底。

#### 4.3.6 结算事务要点

```python
@router.post("/sales/trades")
def submit_trade(data: TradeCreate, db: Session = Depends(get_db)):
    # 1. 幂等校验
    cached = check_idempotent(db, data.request_id, SalTrade)
    if cached:
        return ApiResult.ok(cached)

    try:
        # 2. 校验（支付金额、库存、会员余额/积分）
        validate_payment(data)
        validate_stock(db, data.items)

        # 3. 写主单 + 明细（含商品名/规格/成本价快照）
        trade = create_trade(db, data)
        # 4. 扣库存 + 写库存流水
        deduct_stock(db, trade)
        # 5. 会员余额/积分变动
        if data.member_id:
            apply_member_benefit(db, trade)
        # 6. 更新促销统计
        bump_promotion_stat(db, data)

        db.commit()
        return ApiResult.ok(trade)
    except BusinessError as e:
        db.rollback()
        return ApiResult(code=e.code, message=e.message)
```

> **务必在同一事务内完成**，任一环节失败整体回滚，避免出现"钱收了库存没扣"的脏数据。

#### 4.3.8 关联规则挖掘

```python
# 依赖：pandas + mlxtend
from mlxtend.frequent_patterns import apriori, fpgrowth, association_rules

def run_mining(transactions: pd.DataFrame, params: AnalysisParams):
    algo = fpgrowth if params.algorithm == "FP_GROWTH" else apriori
    freq = algo(transactions, min_support=params.min_support, use_colnames=True)
    rules = association_rules(freq, metric="confidence", min_threshold=params.min_confidence)
    rules = rules[rules["lift"] >= params.min_lift]
    return rules.sort_values("lift", ascending=False)
```

> 挖掘应放入 `BackgroundTasks` 异步执行，避免阻塞请求；`cost_ms` 用 `time.perf_counter()` 精确计时。

## 5 文档说明

### 5.1 字段命名的严格性

本文档中的所有字段名**必须与实现完全一致**（大小写敏感）。前端不做字段映射转换，
字段名不符会直接导致数据不显示。例如：

- 推荐接口的请求字段是 `product_ids`（复数），写成 `product_id` 会导致推荐永远为空；
- 促销明细的字段是 `promo_name`，写成 `label` 会导致收银台促销标签空白。

### 5.2 需求追溯

每个接口都标注了 `FRS-XXX-NNN` 需求编号，可直接对应《详细功能需求文档》第 3 章。
论文的"系统实现"章节可按此映射组织，说明"每个需求由哪个接口实现"。
