## 1 方案依据与目标

### 1.1 设计依据

| 依据 | 用途 |
| --- | --- |
| 《详细功能需求文档》第 3、4 章 | 功能边界与数据需求（126 项功能需求、数据实体与约束） |
| 《后端接口文档》 | **128 个接口的字段诉求**——决定表要供给哪些数据 |
| 前端工程 `qianduan/src` | 实际使用的字段、权限码、状态枚举（最终事实来源） |
| 《数据库设计说明书》 | 表结构权威定义 |
| 实际建库验证 | 脚本可执行性、数据一致性的实测结论 |

### 1.2 设计目标

| 目标 | 具体要求 |
| --- | --- |
| **可追溯** | 每一笔库存、每一次余额变动都能追溯到来源单据，不允许"凭空变化" |
| **可复算** | 任意时点的库存/毛利能独立重算，不依赖"当前值" |
| **不打架** | 并发收银、并发盘点下数据不冲突、不超卖 |
| **说得清** | 关键设计能对应到业务痛点（社区超市的实际场景） |
| **跑得动** | 单店 3～15 人、日交易数百单的规模下无需分库分表 |

### 1.3 设计约束

1. **财务数据必须留痕**：金额相关表只增不改（流水表）。
2. **历史单据不受后续变更影响**：商品改名、进价波动不能污染历史毛利。
3. **人员流动性高**：权限粒度要能精确到按钮，避免误操作。
4. **数据不能真删**：业务数据逻辑删除，保证审计可查。
5. **单机部署优先**：不引入 Redis / 消息队列等外部依赖，降低部署门槛。

## 2 数据架构总览

### 2.1 数据域划分

按"业务内聚 + 变更频率"把 59 张表划为 8 个域：

| 域 | 前缀 | 表数 | 职责 | 变更频率 |
| --- | --- | --- | --- | --- |
| 基础数据域 | `base_` | 4 | 门店、收银台、计量单位、货架 | 极低 |
| 权限与用户域 | `sys_` | 9 | 用户、角色、权限、参数、字典、日志 | 低 |
| 商品域 | `prd_` | 7 | 分类、SPU、商品、条码、价格历史、标签 | 低 |
| 供应商与采购域 | `pur_` | 9 | 供应商、采购单、收货、退货、付款 | 中 |
| 库存域 | `inv_` | 9 | 库存快照、**库存流水**、批次、盘点、报损、调拨 | **高** |
| 会员与促销域 | `mem_` / `pro_` | 10 | 会员、等级、积分/储值流水、促销、优惠券 | 中 |
| 销售域 | `sal_` | 7 | 销售单、明细、支付、退货、挂单、班次 | **高** |
| 智能分析域 | `bi_` | 4 | 分析任务、关联规则、推荐缓存、日统计 | 低（批处理） |

> 域前缀不只是命名习惯，它同时约束了**依赖方向**：
> 上层域可以引用下层域，下层域绝不引用上层域。
> 例如 `inv_` 可以引用 `prd_` 的商品，但 `prd_` 不出现任何库存字段——
> 这从结构上杜绝了循环依赖。

## 3 关键设计决策

> 本章是方案的核心。每条决策按「**业务痛点 → 设计方案 → 权衡取舍 → 实际收益**」展开，
> 可直接作为论文"数据库设计"章节的论证素材。

### 决策一：库存采用「流水驱动」而非「状态维护」

**业务痛点**
社区超市最常见的账实不符是："库存显示 20 件，实际只剩 14 件，但**没人知道那 6 件去哪了**"。
传统做法（只维护一张库存表，每次出入库改数字）丢失了中间过程，盘点差异无法归因，
更无法发现"是不是被内部人员拿走了"。

**设计方案**
引入 `inv_stock_flow` 作为库存的**唯一真相源**，`inv_stock` 降级为它的冗余快照。

- 任何库存变动（采购入库、销售出库、退货、盘点调整、报损、调拨）**都必须写一条流水**；
- 每条流水记录 `flow_type`（变动类型）、`direction`（方向）、`quantity`、**`before_qty` / `after_qty`**、
  `unit_cost`、`source_type` / `source_no`（来源单据）；
- 流水表**只增不改**，物理上不允许更新与删除。

由此获得两条可验证的性质：

```
性质 1（快照一致）：inv_stock.quantity = Σ(flow.quantity × flow.direction)
性质 2（时点可复算）：任意时点 t 的库存 = Σ(截止 t 的流水)
```

**权衡取舍**

| 方案 | 优点 | 缺点 | 取舍 |
| --- | --- | --- | --- |
| 只维护库存表 | 写入快、结构简单 | 过程丢失、差异无法归因 | ✗ |
| 只存流水不维护快照 | 完全可追溯 | 每次查询库存都要聚合，收银台扛不住 | ✗ |
| **流水 + 快照双写** | 可追溯 + 查询快 | 需保证两者一致（写入时必须同事务） | **✓ 采纳** |

代价是**每次库存变动要写两张表**，用事务保证一致性（见第 5.3 节）。

**实际收益**

1. 盘点差异可归因：对比账面流水与实盘数，能定位到"哪一笔出库没记账"；
2. 成本可追溯：`unit_cost` 记录在流水上，毛利可逐笔复算；
3. 审计友好：谁在什么时候动了多少货，流水表一查便知；
4. **进销存报表的勾稽关系可自动校验**：`期初 + 入库 − 出库 = 期末`，
   不成立的行会被标红（见第 5.2 节）。

### 决策二：单据明细采用「快照冗余」

**业务痛点**
商品档案是会变的：改名、调价、换规格。如果销售明细只存 `product_id`，
那么半年后查历史订单时，看到的商品名是**现在的名字**、毛利是按**现在的进价**算的——
历史数据被"污染"了，报表彻底失真。

**设计方案**
在交易类明细表中**冗余存储业务发生时的关键属性**：

| 表 | 冗余字段 | 作用 |
| --- | --- | --- |
| `sal_trade_item` | `product_name`、`spec`、`unit_name`、`unit_price`、`origin_price`、**`cost_price`** | 冻结成交时的商品信息与成本 |
| `pur_order_item` | `product_name`、`spec`、`unit_name` | 冻结下单时的商品信息 |
| `inv_check_item` | `cost_price` | 冻结盘点时的成本 |

**权衡取舍**

这是**刻意的反范式**：数据冗余了，但换来历史数据的正确性。

- 冗余的代价：商品改名后，历史单据仍显示旧名——**这正是想要的效果**；
- 若不冗余：所有历史单据都会"跟随"商品档案变化，审计上不可接受；
- 结论：**交易数据必须冻结在发生的瞬间**，这是财务系统的基本要求。

**实际收益**

毛利报表的口径从此稳定：`毛利 = 应收 − Σ(明细数量 × 明细成本价)`，
而**不是**用商品档案的当前进价——后者会让"上周赚的钱"随本周进价波动而改变。

### 决策三：会员储值采用「本金 / 赠送双轨」

**业务痛点**
"充 100 送 20"是社区超市的常规营销手段，但有个经典漏洞：
顾客充 100 拿到 120，消费 20 后退款，如果系统只有"一个余额字段"，
退款 100（或更多）就会让门店**净亏**。

**设计方案**
`mem_member` 拆成两个独立字段，并各自有独立流水：

| 字段 | 含义 | 可否退款 |
| --- | --- | --- |
| `balance` | 储值本金 | ✅ 未消费部分可退 |
| `gift_balance` | 营销赠送 | ❌ **永不退款** |

配套规则：

1. 充值时按比例拆分，写一条 `mem_balance_flow`（含 `amount` 与 `gift_amount` 两个金额）；
2. 消费时**优先扣赠送余额**，扣完再扣本金（让顾客"先用掉不能退的钱"）；
3. 退款时**只退本金**。

**权衡取舍**

| 方案 | 风险 |
| --- | --- |
| 单一 `balance` 字段 | 赠送金额混入本金，可被退款套利 |
| 双字段但不分流水 | 能算总额，但说不清每笔的钱从哪来 |
| **双字段 + 独立流水** | 结构稍复杂，但每一分钱的来源与去向都可追溯 |

**实际收益**
从**数据结构层面**杜绝了充值套利——不依赖业务代码"记得别退赠送部分"，
而是让"赠送的钱"在物理上就不在可退款的那一列里。

### 决策四：盘点采用「冻结账面快照」

**业务痛点**
盘点要花时间（小超市全盘也要 1～2 小时），但**盘点期间门店照常营业**。
如果用"实时账面数"计算差异，那么盘点过程中卖掉的商品会被误判为盘亏。

**设计方案**
创建盘点单时立即把当时的账面库存**冻结**进 `inv_check_item.snapshot_qty`：

| 字段 | 含义 |
| --- | --- |
| `book_qty` | 实时账面数（会随销售变化） |
| **`snapshot_qty`** | **创建盘点单时冻结的账面数（不随销售变化）** |
| `actual_qty` | 实盘数 |
| `diff_qty` | 差异 = `actual_qty − snapshot_qty` |

**权衡取舍**
多存一个字段，换来差异计算的口径正确。若只用 `book_qty`，
盘点期间每卖出一件商品就会凭空多出一笔"盘亏"，需要人力事后解释——
这正是很多小型系统的真实痛点。

**实际收益**
盘点结果只反映"真实的账实差异"，不掺杂盘点期间的正常销售。

### 决策五：结算接口的「幂等键」

**业务痛点**
收银台网络抖动时，收银员会重复点"结算"。如果没有防护，
一次交易会被记两笔，库存扣两次，会员余额扣两次——**这是资金事故**。

**设计方案**
`sal_trade.request_id` 建**唯一索引**，由前端生成（时间戳 + 随机串）并随请求提交。
后端逻辑：

1. 收到请求先查 `request_id` 是否已存在；
2. 已存在 → **不重复执行**，直接返回首次的处理结果；
3. 不存在 → 执行结算，写入 `request_id`。

最终由数据库的**唯一约束兜底**（并发场景下应用层查重可能同时通过，唯一索引不会）。

**权衡取舍**

| 方案 | 问题 |
| --- | --- |
| 前端按钮置灰防重复 | 防不住网络层重试、用户刷新 |
| 应用层查重 | 并发下存在竞态窗口 |
| **唯一索引 + 结果复用** | 数据库层面保证，是最后一道防线 |

**推广**：同类资金接口都套用该模式——`mem_balance_flow`（会员充值）、
`pur_payment`（供应商付款）同样带幂等键。

### 决策六：成本核算采用「移动加权平均」

**业务痛点**
同一商品每次进价可能不同（生鲜尤其明显）。要算毛利，就必须回答"卖掉的这批，
成本按哪次进价算？"

**方案选型**

| 方法 | 说明 | 适用性 |
| --- | --- | --- |
| 先进先出（FIFO） | 按批次先后结转 | 需严格批次管理，小超市做不到 |
| 个别计价 | 每件单独记成本 | 社区超市不可行 |
| **移动加权平均** | 每次入库后重算平均成本 | **✓ 采纳** |

**计算公式**

```
入库后新成本 = (原库存数量 × 原成本 + 本次入库数量 × 本次入库单价) ÷ (原库存数量 + 本次入库数量)
```

**实现落点**
- `prd_product.avg_cost` 保存当前平均成本（便于展示与快速计算）；
- `inv_stock.avg_cost` 保存分门店的平均成本（多门店成本可能不同）；
- `inv_stock_flow.unit_cost` 记录**本次变动使用的成本**（用于逐笔复算毛利）；
- `sal_trade_item.cost_price` 记录**成交时的成本快照**（历史毛利不被污染）。

**权衡取舍**
移动加权平均牺牲了"精确到批次的成本"，换来**简单可落地**：
只需在采购收货时触发一次重算，无需维护复杂的批次结转逻辑。
对社区超市（毛利粗放、品类周转快）而言，精度足够而成本最低。

### 决策七：业务数据「只停用不物理删除」

**业务痛点**
商品下架、供应商不合作、员工离职、分类调整——如果直接 `DELETE`，
所有引用这些数据的历史单据都会变成"孤儿数据"，
轻则报表显示空白，重则外键报错查不出数据。

**设计方案**

1. **全局禁用级联删除**：86 条外键全部为 `RESTRICT`（详见说明书第 7.2 节）；
2. 业务主数据统一用 `status` 字段标记：`1` 可用 / `0` 停用；
3. 有业务流水的数据**只允许停用**，删除请求由后端拒绝并给出原因。

**唯一的例外**
`base_store.manager_id`（店长）**刻意不建外键**——它与 `sys_user.store_id` 互相引用，
建外键会造成循环依赖，导致两边都无法插入数据。这是经过权衡的"受控妥协"。

**实际收益**
历史单据永远可追溯，审计时不会出现"查不到这个商品"的尴尬。

### 决策八：权限模型采用「RBAC + 数据范围」

详见第 4.4 节（与接口的对应关系）。

**设计要点**
- 用户—角色—权限三级授权（`sys_user_role`、`sys_role_permission` 两张关联表），
  支持**一人多岗**（社区超市常见"收银员兼理货"）；
- 角色额外携带 `data_scope`（`ALL` / `STORE` / `DEPT` / `SELF`），
  实现在同一套权限码下的**数据范围隔离**；
- 权限码与前端路由一一对应，做到**菜单级 + 按钮级**双层控制。

---

### 决策九：分析结果「落表缓存」

**业务痛点**
关联规则挖掘（Apriori / FP-Growth）是**重计算**：几万条交易跑一次要数秒到数十秒。
如果每次打开页面都实时算，用户等不起，数据库也扛不住。

**设计方案**

| 表 | 作用 |
| --- | --- |
| `bi_analysis_task` | 记录每次挖掘任务：参数、耗时 `cost_ms`、结果摘要、状态 |
| `bi_association_rule` | 落库挖掘产出的关联规则（支持度/置信度/提升度/业务解读） |
| `bi_recommend_cache` | 收银台推荐结果缓存（避免每次扫码都查规则表） |
| `bi_daily_stat` | 日粒度经营指标预聚合（报表与大屏的取数来源） |

**实际收益**
1. **算法对比有据可查**：`bi_analysis_task.cost_ms` 记录了每次运行的耗时，
   是论文实验章节"FP-Growth vs Apriori 性能对比"的**原始数据来源**；
2. 收银台推荐走缓存，响应稳定在毫秒级；
3. 报表走预聚合表，避免对交易表做全表扫描。

---

### 决策十：热表索引与归档策略

**业务痛点**
`inv_stock_flow`、`sal_trade`、`sys_operation_log` 是只增表，长期运行会持续膨胀。

**设计方案**

1. **索引设计**（详见说明书 5.2 节）：
   - 流水类表按 `(product_id, created_at)`、`(store_id, created_at)` 建复合索引，
     支撑"某商品某时段"和"某门店某时段"两类高频查询；
   - 交易表按 `(store_id, trade_time)`、`(cashier_id, trade_time)` 建索引；
   - 单据表对单号建唯一索引（`uk_trade_no` 等）。

2. **归档策略**（说明书 5.3 节）：
   - 流水/日志类数据保留 **2 年**，超期按月归档到历史表；
   - 交易数据**永久保留**（财务要求），但通过分区/归档表控制单表规模。

**容量估算**（单店，说明书 9.4 节）
按日均 300 单、每单 6 条明细估算，年增约 65 万条明细、200 万条流水——
对 InnoDB 单表而言完全在舒适区，**无需分库分表**。

## 4 数据与接口的供给关系

> 本章把"表结构"与"接口契约"对齐，回答一个后端实现时必然遇到的问题：
> **接口要的字段，表里有吗？没有的从哪来？**

### 4.1 核对方法

对每个核心数据模型，逐一比对"接口字段集合"与"数据表字段集合"，
把差异分为三类：**直接映射**、**派生字段**、**子表聚合**。

### 4.2 三类供给关系

#### 类型一：直接映射（表字段即接口字段）

绝大多数标量字段属于此类，无需额外处理。例如 `prd_product` 的
`product_code` / `product_name` / `sale_price` / `is_weight` 直接对应
接口 `Product` 模型的同名字段。

#### 类型二：派生字段（需要 JOIN 或计算）

接口比表"多"出来的字段，主要有两种来源：

**（1）关联对象的名称**——表里存的是外键 ID，接口要展示名称

| 接口字段 | 所在接口 | 取数方式 |
| --- | --- | --- |
| `Product.category_name` | 商品列表/详情 | JOIN `prd_category` |
| `Product.unit_name` | 商品列表/详情 | JOIN `base_unit` |
| `Product.stock_qty` | 商品列表 | JOIN `inv_stock` |
| `Product.barcodes` | 商品详情 | 子表 `prd_barcode` 聚合 |
| `StockItem.product_code` / `product_name` / `spec` / `unit_name` | 库存列表 | JOIN `prd_product` + `base_unit` |
| `StockItem.store_name` | 库存列表 | JOIN `base_store` |
| `StockFlow.product_name` | 库存流水 | JOIN `prd_product` |
| `StockFlow.batch_no` | 库存流水 | JOIN `inv_batch`（表内存 `batch_id`） |
| `StockFlow.operator_name` | 库存流水 | JOIN `sys_user`（表内存 `operator` 即用户 ID） |
| `CheckSheet.created_by_name` | 盘点单 | JOIN `sys_user` |
| `CheckSheetItem.product_code` / `product_name` / `spec` | 盘点明细 | JOIN `prd_product` |
| `PurchaseOrder.supplier_name` / `created_by_name` | 采购单 | JOIN `pur_supplier` / `sys_user` |
| `PurchaseOrderItem.product_code` / `product_name` / `spec` / `unit_name` | 采购明细 | JOIN `prd_product` + `base_unit` |
| `Member.level_name` / `discount_rate` | 会员列表/详情 | JOIN `mem_level` |
| `Promotion.created_by_name` | 促销列表 | JOIN `sys_user` |
| `PromotionItem.target_name` | 促销详情 | JOIN `prd_product` 或 `prd_category` |
| `Trade.cashier_name` / `member_name` / `member_no` | 销售单 | JOIN `sys_user` / `mem_member` |
| `SaleReturn.source_trade_no` / `operator_name` | 退货单 | JOIN `sal_trade` / `sys_user` |
| `SaleSession.pos_name` / `cashier_name` | 交班单 | JOIN `base_pos` / `sys_user` |
| `SysUser.store_name` | 用户列表 | JOIN `base_store` |
| `SysRole.user_count` | 角色列表 | 聚合 `sys_user_role` |
| `RecommendItem.product_code` / `product_name` / `spec` / `sale_price` | 收银台推荐 | JOIN `prd_product` |

**（2）计算字段**——表里不存，实时算出来

| 接口字段 | 计算口径 |
| --- | --- |
| `StockItem.stock_status` | 由 `quantity` / `safe_qty` / `remain_days` 判定：`LOW`（≤安全库存）/ `OVER`（>上限）/ `NEAR_EXPIRY`（临近保质期）/ 否则 `NORMAL` |
| `StockItem.stock_amount` | `quantity × avg_cost` |
| `StockItem.remain_days` | `inv_batch.expiry_date − 当前日期` |
| `Member.sleeping_days` | `当前日期 − last_consume_at` |

> **为什么不落库？** 这类字段会随时间自动变化（今天不是临期，明天就是了）。
> 落库就必须定时刷全表，既浪费又容易不一致。**实时算是最可靠的。**

#### 类型三：子表聚合（一对多）

父单接口返回的 `items` / `payments` 数组来自子表：

| 接口字段 | 来源表 |
| --- | --- |
| `Trade.items` | `sal_trade_item` |
| `Trade.payments` | `sal_trade_payment` |
| `PurchaseOrder.items` | `pur_order_item` |
| `CheckSheet.items` | `inv_check_item` |
| `Promotion.items` | `pro_promotion_item` |

**实现建议**：列表接口**不要**返回子表（避免 N+1 查询），
详情接口一次性用 `IN` 批量取回子表再组装。

### 4.3 命名差异的处理原则

核对中发现少数"表字段名 ≠ 接口字段名"的情况，**统一按下列原则处理**：

| 场景 | 表字段 | 接口字段 | 处理 |
| --- | --- | --- | --- |
| 表存外键 ID，接口要名字 | `operator` (ID) | `operator_name` | 后端 JOIN 后输出名字，**不改表结构** |
| 表存外键 ID，接口要编号 | `batch_id` (ID) | `batch_no` | JOIN `inv_batch` 取 `batch_no` |
| 表存外键 ID，接口要名字 | `created_by` (ID) | `created_by_name` | JOIN `sys_user` |

**为什么不直接改表字段名？**
数据库存 **ID** 是规范做法（省空间、防数据不一致、支持改名）；
接口返回 **名称** 是展示需要。两者的分工是清晰的：
**表负责"存储正确"，接口负责"展示友好"**，中间的转换由后端完成。

## 5 一致性与完整性保障

### 5.1 三层约束体系

数据正确性不能只靠应用代码"记得校验"，方案在**三个层次**上层层设防：

| 层次 | 手段 | 例子 |
| --- | --- | --- |
| **第一层：数据类型与约束** | `NOT NULL`、`DEFAULT`、`UNIQUE`、`CHECK` | 金额 `DECIMAL(12,2)` 不会出现浮点误差；`request_id` 唯一索引挡住重复结算 |
| **第二层：参照完整性** | 86 条外键（全部 `RESTRICT`） | 不能删除被单据引用的商品；不能给不存在的门店挂库存 |
| **第三层：业务规则** | 后端服务层校验 + 事务 | 盘点差异必须填原因；支付总额必须等于应收 |

**为什么外键一律用 `RESTRICT` 而不是 `CASCADE`？**
级联删除在财务系统里是危险的——删一个商品连带删掉历史销售明细，
数据就再也无法审计。方案选择**宁可删不掉，也不误删**。

### 5.2 勾稽校验：让数据"自证清白"

方案设计了若干**可在数据库中直接验证的恒等式**，用于发现数据不一致：

#### 校验一：库存快照与流水一致（决策一的直接推论）

```sql
-- 应当返回空结果集；有返回行说明 snapshot 与 flow 不一致
SELECT s.product_id, s.quantity AS snapshot_qty,
       IFNULL(SUM(f.quantity * f.direction), 0) AS flow_qty
FROM inv_stock s
LEFT JOIN inv_stock_flow f
  ON f.product_id = s.product_id AND f.store_id = s.store_id
GROUP BY s.product_id, s.quantity
HAVING ABS(s.quantity - IFNULL(SUM(f.quantity * f.direction), 0)) > 0.0001;
```

#### 校验二：进销存报表勾稽（会计恒等式）

```
期初库存 + 本期入库 − 本期出库 = 期末库存
```

报表接口返回 `begin_qty` / `in_qty` / `out_qty` / `end_qty` 四个字段，
前端对不成立的行**标红提示**——把数据校验变成**用户可见的功能**，
而不是藏在日志里。

#### 校验三：销售单金额自洽

```
应收金额 = 优惠前总额 − 优惠合计
实收金额 = Σ 支付明细金额
毛利 = 应收金额 − Σ(明细数量 × 明细成本价)
```

#### 校验四：储值双轨平衡

```
mem_member.balance      = Σ(mem_balance_flow.amount × direction)
mem_member.gift_balance = Σ(mem_balance_flow.gift_amount × direction)
```

> **这四条恒等式的价值**：它们把"数据一致性"从口头承诺变成**可执行的 SQL**。
> 定期跑一遍，就能主动发现问题，而不是等用户投诉账不对。

### 5.3 事务边界设计

涉及多表写入的业务，**必须在同一事务内完成**，任一步失败整体回滚。

#### 事务 T1：收银结算（最关键）

```
BEGIN
  1. 幂等校验        → 查 sal_trade.request_id，已存在则直接返回
  2. 业务校验        → 支付金额 = 应收、库存充足、会员余额/积分充足
  3. 写销售主表      → sal_trade（含 request_id）
  4. 写销售明细      → sal_trade_item（含商品名/成本价快照）
  5. 写支付明细      → sal_trade_payment（支持混合支付）
  6. 扣减库存        → UPDATE inv_stock
  7. 写库存流水      → INSERT inv_stock_flow（SALE_OUT）
  8. 会员权益        → 扣余额/加积分 + 写 mem_balance_flow / mem_point_flow
  9. 更新会员累计    → total_consume / consume_count，判断等级升级
 10. 更新促销统计    → trigger_count / discount_total
COMMIT
```

**为什么必须一个事务？** 否则可能出现"钱收了、库存没扣"或"库存扣了、流水没写"，
后续对账时无法定位。

#### 事务 T2：采购收货与成本重算

```
BEGIN
  1. 校验订单状态允许收货（状态机）
  2. 写收货单 + 收货明细
  3. 累加 pur_order_item.received_qty，判断是否收货完毕
  4. 增加 inv_stock
  5. 写 inv_stock_flow（PURCHASE_IN）
  6. 写/更新 inv_batch（保质期商品）
  7. 重算移动加权平均成本 → 更新 avg_cost
COMMIT
```

#### 事务 T3：盘点审核

```
BEGIN
  1. 校验盘点单状态为 SUBMITTED
  2. 校验每一条差异明细都填了 diff_reason
  3. 按差异调整 inv_stock
  4. 写 inv_stock_flow（CHECK_ADJUST，逐条）
  5. 盘点单状态置 AUDITED
COMMIT
```

#### 事务 T4：会员充值（幂等）

```
BEGIN
  1. 幂等校验（request_id）
  2. 拆分为本金 amount 与赠送 gift_amount
  3. 更新 mem_member.balance / gift_balance
  4. 写 mem_balance_flow（含 before/after 双方余额）
COMMIT
```

### 5.4 并发控制

社区超市的并发压力集中在**收银台**，方案采取以下措施：

| 场景 | 风险 | 措施 |
| --- | --- | --- |
| 同一商品被两个收银台同时卖出 | 超卖 | 扣库存用 `UPDATE ... WHERE quantity >= ?` 条件更新，受影响行数为 0 即库存不足 |
| 重复提交结算 | 重复扣款 | `request_id` 唯一索引 |
| 并发扣会员余额 | 余额变负 | 同样用条件更新 `WHERE balance >= ?` |
| 单据状态并发流转 | 状态错乱 | 状态机校验 + 条件更新（`WHERE status = 'DRAFT'`） |

**设计倾向**：优先用**数据库的原子条件更新**解决并发，
而不是应用层加锁——后者在单机部署下更复杂，且容易死锁。

## 7 设计权衡与局限

任何设计都有边界。本节如实说明方案的取舍与不足。

### 7.1 为什么不做分库分表

**结论：当前规模不需要，做了反而增加复杂度。**

容量测算（单店）：

| 表 | 日增估算 | 年增估算 |
| --- | --- | --- |
| `sal_trade` | 300 条 | 约 11 万条 |
| `sal_trade_item` | 1,800 条 | 约 65 万条 |
| `inv_stock_flow` | 约 2,000 条 | 约 73 万条 |
| `sys_operation_log` | 约 1,000 条 | 约 36 万条 |

百万级数据量对 MySQL 单表完全在舒适区（配合索引，查询仍在毫秒级）。
即使按 5 家门店估算，也不过数百万行，**分库分表带来的分布式事务、
跨库查询、运维复杂度远超收益**。

方案选择的是更轻的策略：**索引优化 + 冷热分离归档**。

### 7.2 报表性能的取舍

**问题**：经营看板与报表需要聚合大量交易数据，实时算会很慢。

**方案**：分层处理。

| 场景 | 策略 |
| --- | --- |
| 实时性要求高（今日数据） | 直接查交易表 + 索引优化，接受百毫秒级 |
| 历史趋势（30 天曲线） | 查 `bi_daily_stat` 预聚合表 |
| 复杂分析（关联规则） | 异步任务 + 结果落表，前端轮询 |

**取舍**：预聚合表存在**数据延迟**（通常是 T+1 或定时刷新），
换来的是报表页面的响应速度。对于经营分析场景，这个延迟是可接受的。

### 7.3 已知局限

| 局限 | 说明 | 影响 |
| --- | --- | --- |
| 成本精度 | 移动加权平均不区分批次成本 | 生鲜类毛利核算有少量误差，业务可接受 |
| 预聚合延迟 | `bi_daily_stat` 非实时 | 当日报表可能有延迟 |
| 单库单表 | 未做水平扩展 | 门店数超过约 20 家时需要重新评估 |
| 逻辑删除累积 | 停用数据长期保留 | 主数据表会缓慢增长（但量级很小） |
| 无软删除标记 | 业务表用 `status` 而非统一的 `is_deleted` | 各表语义不同（`status` 含义按表定义），一致性稍弱 |

### 7.4 后续演进方向

若系统需要继续扩展，建议按此顺序推进：

1. **读写分离**：报表查询走从库，与收银事务隔离；
2. **引入缓存**：把商品档案、权限数据放入 Redis，减少热点查询；
3. **冷热分离**：流水与日志按月归档到历史表，主表只留热数据；
4. **分区表**：对 `inv_stock_flow` / `sal_trade_item` 按时间分区；
5. **数据仓库**：分析类需求迁移到列式存储（如 ClickHouse），支撑更复杂的 BI。

## 8 方案总结

### 8.1 方案成果

| 维度 | 成果 |
| --- | --- |
| 规模 | 8 个数据域 / 59 张表 / 86 条外键 |
| 覆盖 | 完整支撑 11 个功能模块、128 个接口、36 个前端页面 |
| 规范 | 统一主键、统一金额/数量精度、统一审计字段、统一命名前缀 |
| 验证 | 建库实测通过、权限码零差异、库存勾稽零不一致 |

### 8.2 方案特点

1. **以"可追溯"为第一原则**——库存流水、资金流水、操作日志三张只增表，
   构成系统的"事实链"，任何变动都有据可查；
2. **用结构解决问题，而非用代码打补丁**——储值双轨从字段层面杜绝套利，
   幂等键从索引层面杜绝重复扣款；
3. **刻意的反范式换取正确性**——交易明细冗余快照，让历史数据不随主数据漂移；
4. **数据自证**——设计可执行的勾稽校验，把一致性从承诺变成可验证的 SQL；
5. **面向落地**——不做过度设计，单机可部署，与需求规模匹配。
