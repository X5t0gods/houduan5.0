## 1 概述

### 1.1 编写目的

本文档是"基于 FastAPI 的中小型社区超市销售管理系统"的数据库设计成果说明，承接《详细功能需求文档》中第 4 章的数据需求，向下指导具体的数据表创建、数据访问层编码与测试数据的构造。

本文档要达成四个目标：

1. **固化数据结构**：明确 59 张数据表的字段构成、类型、约束与相互关系，作为开发阶段"唯一且不再随意变更"的数据基准。
2. **体现设计过程**：完整呈现"需求分析 → 概念结构设计（E-R）→ 逻辑结构设计（关系模式）→ 物理结构设计（DDL）"的规范化设计路径，满足毕业论文对设计方法论的考察要求。
3. **保障数据质量**：通过主键、外键、唯一约束、业务约束四层机制，保证数据的正确性、一致性与可追溯性。
4. **支撑性能目标**：通过索引设计、聚合表设计与归档策略，支撑需求文档中 NFR-P 系列的性能指标。

## 2 数据库设计规范

### 2.1 设计原则

| 编号 | 原则 | 说明 |
| --- | --- | --- |
| DP-01 | **流水驱动库存** | `inv_stock_flow` 是库存数量的唯一真相源，`inv_stock` 只是它的事务化冗余快照。任何库存变动必须由单据产生，禁止绕过流水直接改库存数字 |
| DP-02 | **单据不可变** | 销售单、收货单、盘点单等单据一经审核即不可修改，只能通过反向单据（退货单、调整单）冲正，保证审计链路完整 |
| DP-03 | **金额零误差** | 所有金额使用 DECIMAL(12,2)，禁止 FLOAT/DOUBLE；成本用 DECIMAL(12,4) 保留四位小数以减少累计误差 |
| DP-04 | **快照留痕** | 交易明细冗余存储商品名称、规格、单位、单价、成本价，保证商品资料变更后历史单据与历史毛利仍然准确 |
| DP-05 | **主数据只停用不删除** | 被业务引用的商品、供应商、会员等主数据只能置为停用状态，保证历史单据可追溯 |
| DP-06 | **时间字段双轨** | 业务时间（`trade_time`、`received_at`）与系统时间（`created_at`）分开存储，便于区分"业务发生时刻"与"记录写入时刻" |
| DP-07 | **适度冗余换性能** | 报表类查询通过 `bi_daily_stat` 聚合表与 `avg_cost` 冗余字段换取查询性能，冗余字段由服务层在同事务内维护一致性 |
| DP-08 | **命名即文档** | 表名、字段名、注释均使用可读的业务语义，避免拼音缩写与无意义代号 |

| 类别 | 规范 | 示例 |

### 2.3 数据类型规范

| 用途 | 类型 | 精度 | 说明 |
| --- | --- | --- | --- |
| 主键 / 外键 | `BIGINT UNSIGNED` | — | 支持超大数据量，无负数需求 |
| 金额 | `DECIMAL(12,2)` | 12 位整数 + 2 位小数 | 支持百亿元级金额，禁止浮点 |
| 成本单价 | `DECIMAL(12,4)` | 4 位小数 | 减少移动加权平均的累计舍入误差 |
| 折扣率 | `DECIMAL(5,4)` | 0.9500 表示 95 折 | 与 DECIMAL(12,2) 金额配合 |
| 商品数量 | `DECIMAL(12,3)` | 3 位小数 | 支持称重商品的克级精度 |
| 聚合表金额 | `DECIMAL(14,2)` | 14 位 | 汇总值位数放大，防止溢出 |
| 布尔语义 | `TINYINT` | 1/0 | 便于扩展为多状态 |
| 枚举语义 | `VARCHAR(16/24)` | — | 使用可读字符串，便于调试与扩展 |
| 短文本 | `VARCHAR(32/64)` | — | 名称、编码 |
| 长文本 | `VARCHAR(200/255)` | — | 地址、备注 |
| 结构化数据 | `JSON` | — | 购物车快照、参数、前后值快照 |
| 时间 | `DATETIME` / `DATE` / `TIME` | — | 业务时区统一为门店本地时间 |

**为什么枚举用 VARCHAR 而不是 TINYINT**：状态码使用可读字符串（如 `PARTIAL`、`FINISHED`）虽然占用略多空间，但在数据库直接查询、日志排查、跨语言联调时无需查字典表即可理解语义，对小型项目而言可维护性收益大于空间开销。字典表 `sys_dict` 用于前端下拉选项渲染，与字段值保持同步。

**（3）状态字段取值约定**

| 业务对象 | 状态取值 |
| --- | --- |
| 采购订单 | `DRAFT` 待审核 → `AUDITED` 已审核 → `PARTIAL` 部分收货 → `RECEIVED` 已收货 → `FINISHED` 已完成 ／ `VOID` 已作废 |
| 盘点单 | `DRAFT` 盘点中 → `SUBMITTED` 待审核 → `AUDITED` 已审核 ／ `VOID` 已作废 |
| 销售单 | `FINISHED` 已完成 → `RETURNED` 已退货 ／ `VOID` 已作废 |
| 收银班次 | `OPEN` 营业中 → `CLOSED` 待审核 → `AUDITED` 已审核 |
| 促销规则 | `DRAFT` 未开始 → `RUNNING` 进行中 → `STOPPED` 已停用 ／ `EXPIRED` 已结束 |
| 退款 | `PENDING` 待退款 → `REFUNDED` 已退款 ／ `FAILED` 退款失败 |
| 通用启用状态 | `1` 启用 ／ `0` 停用 |

**（4）时间字段的时区约定**

需求文档 CON-07 规定：**时间统一按门店本地时区存储与展示**。因此数据库连接层不启用时区转换（禁用 `USE_TZ` 式行为），所有 DATETIME 字段写入的即为门店墙上时间。这一约定直接影响按日聚合的准确性——若启用时区转换，`DATE(created_at)` 会因 UTC 偏移把深夜的交易归入前一天。

## 3 概念结构设计

### 3.1 设计方法

概念结构设计采用**自底向上**的策略，分四步完成：

1. **识别实体**：从需求文档的功能描述中提取名词性概念，区分"独立存在的对象"（商品、会员、供应商）与"依附存在的对象"（销售明细、积分流水）。
2. **确定属性**：为每个实体确定标识属性（主键候选）与描述属性，剔除可由其他属性推导的冗余属性（如"年龄"由出生日期推导，不入库）。
3. **确定联系**：分析实体之间的业务动作，确定联系类型（1:1 / 1:N / M:N）与联系的属性（如"供货"联系带供货价）。
4. **绘制 E-R 图**：采用陈氏表示法（矩形=实体、菱形=联系、椭圆=属性从略、连线标注基数），按主题域拆分为三张子图，避免单图过度拥挤。

**关于属性椭圆的处理说明**：完整的陈氏 E-R 图会为每个实体绘制数十个属性椭圆，在实体数量达到数十个时会导致图形不可读。本设计采用学术论文中的常见折中做法——**E-R 图只表达实体与联系，属性通过第 6 章的关系模式表完整定义**。

### 3.4 概念模型 E-R 图

按照主题域拆分为三张 E-R 图，分别表达"商品与采购""库存与销售""会员与支撑域"三组核心概念。

**（一）商品主数据与采购供应链**

覆盖商品主数据（分类、单位、条码）与采购链条（供应商 → 采购单 → 收货单）。核心是"商品"实体，它同时被采购、库存、销售三条业务链引用。

![图 3-1  商品主数据与采购供应链 E-R 图](ER图1_商品与采购.png)

该图突出两点设计：其一，「供货」是带属性的多对多联系，其属性（供货价、最近采购时间）随联系产生，因此转换为独立的 `pur_supplier_product` 关系表；其二，「请购」同样是多对多联系，属性（数量、单价、已收数量）落地为 `pur_order_item`。这两处是 E-R 转换中最容易被简化为"外键"而丢失属性的典型场景。

**（二）库存流转与销售收银**

覆盖库存的进销存流转与销售收银链路。「库存」是"商品×门店"组合实体，与商品、门店均为 M:N，因此独立成表并带唯一约束。

![图 3-2  库存流转与销售收银 E-R 图](ER图2_库存与销售.png)

该图的核心逻辑是**流水驱动**：库存的每一次变化都对应一条 `inv_stock_flow` 记录，记录变动前后的库存值，从而保证任何时点的库存都可以被复算和审计。销售单与支付记录是 1:N 关系，用以支持现金+微信+储值的混合支付场景。

**（三）会员资产、促销规则、权限控制与智能分析**

覆盖会员资产（等级、储值、积分）、促销规则、RBAC 权限模型与智能分析的关联规则。

![图 3-3  会员资产与支撑域 E-R 图](ER图3_会员促销与支撑域.png)

该图中「关联」是商品实体上的**自反多对多联系**——规则的前件与后件都是商品集合，因此 `bi_association_rule` 表用 JSON 字段存储前后件，而不是用两张关联表。

## 4 逻辑结构设计

### 4.1 E-R 图向关系模式的转换规则

本设计严格遵循标准转换规则：

| 规则 | 适用场景 | 转换做法 | 本设计实例 |
| --- | --- | --- | --- |
| R1 | 独立实体 | 转为一张表，实体标识属性作主键 | 商品 → `prd_product` |
| R2 | 1:1 联系 | 合并到任一端，或独立成表 | 本系统无典型 1:1 联系 |
| R3 | 1:N 联系 | 把"1"端主键作为"N"端的外键 | 分类 → 商品：商品表加 `category_id` |
| R4 | M:N 联系 | **必须独立成表**，主键为两端主键的组合，联系属性作为表的字段 | 供货 → `pur_supplier_product`；售出 → `sal_trade_item` |
| R5 | 多度联系 | 独立成表，含所有参与实体的主键 | 本系统通过拆分避免三元联系 |
| R6 | 自反联系 | 同表内自引用，或独立成表 | 商品分类的 `parent_id` 自引用；商品关联用独立表 |
| R7 | 弱实体 | 转为表，主键含宿主实体主键（复合主键或代理主键+唯一约束） | 销售明细 `sal_trade_item` |

**关于代理主键的选择**：规则 R4/R7 理论上应使用"两端主键组合"作为复合主键。本设计统一改用 `BIGINT UNSIGNED AUTO_INCREMENT` 代理主键，并对业务唯一组合加 `UNIQUE KEY`（如 `uk_store_product(store_id, product_id)`）。这样做的好处是：① 关联表被其他表引用时只需单字段外键；② 主键索引更窄，提升插入性能；③ 便于分库分表时调整。业务唯一性由唯一索引保证，语义上不损失约束强度。

| 范式 | 符合情况 | 说明 |
| --- | --- | --- |
| 1NF | 符合 | 所有字段均为原子值。`antecedent` / `cart_json` 等 JSON 字段虽为复合结构，但其语义是"整体暂存"而非可查询的关系数据，不违反 1NF 的设计初衷 |
| 2NF | 符合 | 所有表使用单字段代理主键，不存在非主属性对复合主键的部分依赖 |
| 3NF | 符合 | 无传递依赖。例外是刻意引入的冗余字段（见下） |
| BCNF | 基本符合 | 商品编码、单号等业务键均为候选键，决定因素均包含候选键 |

**关于刻意的反范式设计**（这是本设计需要重点向评审判释的部分）：

| 冗余字段 | 所在表 | 冗余来源 | 引入原因 | 一致性保障 |
| --- | --- | --- | --- | --- |
| `product_name` / `spec` / `unit_name` | `sal_trade_item` | `prd_product` | 商品改名后历史小票与报表必须显示当时的名称 | 写入时取快照，之后不再更新 |
| `cost_price` | `sal_trade_item` | `inv_stock.avg_cost` | 后续进货价变化不得影响历史毛利 | 出库瞬间锁定 |
| `avg_cost` | `inv_stock` | `inv_stock_flow` 推算 | 每次出库都要用当前成本，实时推算代价高 | 每次入库后在同事务内重算 |
| `balance_payable` | `pur_supplier` | 采购、退货、付款三类单据汇总 | 查询供应商欠款需扫描大量单据 | 单据过账时同事务增减 |
| `sale_amount` / `cash_amount` 等 | `sal_session` | `sal_trade` 汇总 | 交班对账需要即时汇总 | 每笔交易完成后同事务累加 |
| `total_consume` / `consume_count` / `points` | `mem_member` | 销售单与积分流水 | 会员列表高频展示，实时汇总成本高 | 交易完成后同事务更新 |
| `trigger_count` / `discount_total` | `pro_promotion` | `sal_trade_item` | 促销效果分析需快速展示 | 每笔命中促销的交易累加 |
| `bi_daily_stat` 全部字段 | 明细表 | 经营看板需要秒级响应 | 定时任务每日凌晨预计算 |

这些冗余字段全部采用"**写入时同事务更新**"策略，绝不允许异步补写，从而在保证性能的同时不破坏一致性。这一设计取舍是数据库设计中"规范化"与"性能"之间权衡的典型体现。

## 5 物理结构设计

### 5.1 存储引擎与字符集

| 项目 | 取值 | 说明 |
| --- | --- | --- |
| 存储引擎 | InnoDB | 支持事务、行级锁、外键约束，是唯一满足本系统一致性要求的选择 |
| 字符集 | utf8mb4 | 支持中文与 emoji（如会员昵称中的表情符号） |
| 排序规则 | utf8mb4_general_ci | 大小写不敏感，查询性能优于 unicode_ci |
| 行格式 | DYNAMIC（MySQL 8.0 默认） | 支持变长字段与 JSON 的溢出页存储 |
| 时区 | 门店本地时间 | 见 2.4 节说明 |

**为什么必须用 InnoDB**：本系统的核心业务动作（收银结算、收货入库、盘点调整）都是"多表写入 + 库存更新 + 成本重算"的组合操作，必须依赖事务的原子性。MyISAM 不支持事务，一旦收银过程中断就会出现"已扣库存但未记销售"的脏数据，因此不在选型考虑范围内。

### 5.2 索引设计

**（1）索引设计原则**

1. **主键索引**：每表必备，采用自增 BIGINT，保证插入时顺序写入、避免页分裂。
2. **唯一索引**：所有业务唯一键（单号、编码、条码、手机号）建立唯一索引，既保证约束又提供查询加速。
3. **外键索引**：MySQL 在创建外键时会自动为外键列创建索引，无需重复定义。
4. **复合索引遵循最左前缀**：按"等值条件列在前、范围条件列在后"的顺序组织。
5. **覆盖高频查询路径**：为收银、库存查询、报表三类高频场景定制索引。

**（2）关键索引清单**

| 表 | 索引名 | 类型 | 字段 | 服务的查询场景 |
| --- | --- | --- | --- | --- |
| `prd_product` | `uk_product_code` | 唯一 | `product_code` | 编码精确定位 |
| `prd_product` | `idx_name` | 普通 | `product_name` | 收银台关键字搜索 |
| `prd_barcode` | `uk_barcode` | 唯一 | `barcode` | **扫码枪输入（最高频，单条查询 < 5ms）** |
| `inv_stock` | `uk_store_product` | 唯一 | `store_id, product_id` | 库存精确定位 |
| `inv_stock_flow` | `idx_product_time` | 复合 | `product_id, created_at` | 商品进出明细 |
| `inv_stock_flow` | `idx_source` | 复合 | `source_type, source_no` | 按单据反查流水（对账） |
| `sal_trade` | `uk_trade_no` | 唯一 | `trade_no` | 单号查询、打印重打 |
| `sal_trade` | `uk_request_id` | 唯一 | `request_id` | **结算幂等校验** |
| `sal_trade` | `idx_store_time` | 复合 | `store_id, trade_time` | 销售日报、时段分析 |
| `sal_trade_item` | `idx_product_time` | 复合 | `product_id, created_at` | 商品销售排行 |
| `mem_member` | `uk_phone` | 唯一 | `phone` | 会员识别 |
| `mem_balance_flow` | `idx_member_time` | 复合 | `member_id, created_at` | 储值流水查询 |
| `bi_association_rule` | `idx_lift` | 普通 | `lift` | 按提升度排序取 TOP N |
| `bi_daily_stat` | `uk_date_store` | 唯一 | `stat_date, store_id` | 看板按日取数 |

**（3）索引开销的权衡**

索引并非越多越好。本系统在以下位置**刻意不建索引**：

- 状态字段（`status`）单独不建索引：状态取值基数低（通常 2~5 个值），单列索引选择性差，MySQL 优化器通常不会使用；如需按状态筛选，走与时间字段的复合索引。
- 备注类字段（`remark`）不建索引：不参与查询条件。
- 布尔字段（`is_weight`、`is_perishable`）不建索引：同上，选择性过低。

### 5.3 大表处理与归档策略

按业务量估算，需要重点关注的大表及处理策略：

| 表 | 预估年增长 | 处理策略 |
| --- | --- | --- |
| `sal_trade_item` | 单店约 100 万行/年 | 按月分区或按年归档；报表查询走 `bi_daily_stat` 聚合表 |
| `inv_stock_flow` | 单店约 50 万行/年 | 按月分区；仅保留近 2 年明细，更早数据归档到历史表 |
| `sys_operation_log` | 约 10 万行/年 | 保留近 6 个月，更早数据导出归档 |
| `sys_login_log` | 约 5 万行/年 | 保留近 3 个月 |
| `mem_point_flow` / `mem_balance_flow` | 约 20 万行/年 | 保留全量（涉及资金，不可归档删除） |

**分区方案示例**（`inv_stock_flow` 按月分区）：

```sql
ALTER TABLE inv_stock_flow
PARTITION BY RANGE (TO_DAYS(created_at)) (
  PARTITION p202609 VALUES LESS THAN (TO_DAYS('2026-10-01')),
  PARTITION p202610 VALUES LESS THAN (TO_DAYS('2026-11-01')),
  PARTITION pmax    VALUES LESS THAN MAXVALUE
);
```

注意：**含外键的表在 MySQL 中无法直接使用分区**。因此实际实施时，`inv_stock_flow` 若需分区，应移除其物理外键约束，改由应用层保证引用完整性。这是本设计在实施阶段需要根据实际数据量做出的取舍——在数据量未达到百万级之前，建议保留外键约束而不分区。

### 5.4 备份与恢复的物理设计

| 项目 | 方案 |
| --- | --- |
| 备份工具 | `mysqldump`（逻辑备份），生成 `.sql` 文件后压缩为 `.sql.gz` |
| 备份频率 | 每日 23:30 自动全量备份 + 支持管理员手动触发 |
| 保留策略 | 保留最近 30 份，超出自动清理最旧文件 |
| 备份内容 | 结构 + 数据 + 事务日志位点（用于增量恢复） |
| 恢复方式 | 全量恢复 + binlog 增量回放，可恢复至任意时间点 |
| 备份文件存储 | 独立目录，文件加密，仅 ADMIN 角色可下载 |
| 校验机制 | 备份完成后校验文件大小与 checksum，记录到备份日志表 |

## 7 数据完整性设计

数据库的完整性通过四层机制逐级保障：**主键保证行的唯一 → 外键保证行间引用有效 → 约束保证字段取值合法 → 业务规则保证语义正确**。

### 7.1 实体完整性

| 机制 | 实现方式 | 说明 |
| --- | --- | --- |
| 主键约束 | 每表 `id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY` | 自增主键保证行唯一，且插入顺序写入、避免索引页分裂 |
| 业务键唯一 | 唯一索引 | 商品编码、单号、条码、手机号、门店编码等业务标识均加唯一索引 |
| 组合唯一 | 复合唯一索引 | `inv_stock(store_id, product_id)` 保证同一门店同一商品只有一行库存；`sal_trade(request_id)` 保证结算幂等 |
| 关联表去重 | 复合唯一索引 | `sys_user_role(user_id, role_id)`、`prd_product_tag(product_id, tag_id)` 等防止重复绑定 |

**为什么用代理主键而非业务主键**：若用 `product_code` 作为主键，商品编码规则一旦调整（如补位、改前缀）将牵动所有引用它的表。采用无业务含义的自增 id 作主键，业务编码作为独立字段加唯一索引，可在不影响任何外键的前提下修改编码规则。

### 7.2 参照完整性

**（1）外键约束策略**

系统共建 **86 条外键约束**，覆盖所有单据与主数据、明细与主表、流水与业务对象之间的引用关系。

| 场景 | 外键策略 | 理由 |
| --- | --- | --- |
| 明细表 → 主表 | `RESTRICT`（默认） | 有明细的主表不可被删除，只能作废 |
| 单据 → 主数据 | `RESTRICT` | 有业务流水的商品/供应商不可被物理删除（配合"只停用不删除"原则） |
| 流水 → 商品/门店 | `RESTRICT` | 流水是审计依据，不允许因主数据变动而失效 |
| 日志 → 用户 | 允许 NULL | 用户被删除后日志仍需保留，故 `user_id` 可为空 |

**（2）为什么不使用 ON DELETE CASCADE**

本系统**全局禁用级联删除**。原因在于零售系统的数据具有强审计属性：删除一个门店若级联删除其全部销售单、库存流水，等同于销毁经营记录，既不符合业务要求，也可能违反财务留痕要求。所有"删除"操作在业务上都被转换为"停用"（`status = 0`）或"作废"（`status = 'VOID'`）。

**（3）循环依赖的处理**

`base_store.manager_id` 与 `sys_user.store_id` 构成循环引用（门店的店长是一个用户，用户又属于门店）。MySQL 无法在两张表上互相加外键，因此本设计在 `base_store.manager_id` 上**不设外键约束**，改由应用层在设置店长时校验用户存在性。这是本设计中唯一一处有意放弃物理外键的位置，已在字段注释中明确标注。

### 7.3 用户定义完整性

| 机制 | 应用位置 | 示例 |
| --- | --- | --- |
| `NOT NULL` | 业务必填字段 | `product_name`、`quantity`、`unit_price` |
| `DEFAULT` | 状态、数量、金额类字段 | `status DEFAULT 1`、`quantity DEFAULT 0.000` |
| 类型约束 | 全表 | 金额 `DECIMAL(12,2)` 天然拒绝非数值输入 |
| 唯一约束 | 见 7.1 节 | — |

**关于 CHECK 约束的说明**：MySQL 8.0.16 起支持 `CHECK` 约束。本设计**未大量使用 CHECK**，理由如下：

1. 零售系统的多数取值约束是**动态的**（如"售价 ≥ 进价"这一规则在清仓促销时会被有意打破），写成硬性 CHECK 反而阻碍业务；
2. 这类约束需要配合"操作人 + 原因"的授权流程，更适合放在服务层并结合权限校验与操作日志实现；
3. 少数静态约束（如"实收金额 ≥ 0"）已在应用层通过 Pydantic 模型校验，双重校验的价值有限。

若需在数据库层补充兜底约束，建议仅对以下字段添加：

```sql
ALTER TABLE sal_trade ADD CONSTRAINT ck_trade_amount CHECK (receivable >= 0);
ALTER TABLE inv_stock ADD CONSTRAINT ck_stock_qty    CHECK (quantity >= -99999);
ALTER TABLE mem_member ADD CONSTRAINT ck_member_bal  CHECK (balance >= 0 AND gift_balance >= 0);
```

注意 `inv_stock.quantity` 的 CHECK 下限设为负数而非 0，是为了在"允许负库存"参数开启时留出空间（社区超市偶尔出现先卖后补录的情况）。

### 7.4 关键业务约束的数据库实现

| 编号 | 业务规则 | 实现层次 | 具体做法 |
| --- | --- | --- | --- |
| BR-01 | 库存不可凭空变动 | 表设计 | 库存只由 `inv_stock_flow` 驱动，`inv_stock` 为派生快照；服务层不提供直接改库存数量的接口 |
| BR-02 | 结算不会重复扣款 | 唯一索引 | `sal_trade.request_id` 唯一，重复提交触发唯一键冲突并按幂等返回原单 |
| BR-03 | 单号不会重复 | 唯一索引 + 序列生成 | 单号由服务端"日期 + 序列"生成并加唯一索引兜底 |
| BR-04 | 退货数量不超过原单 | 服务层校验 | 校验 `SUM(sal_return_item.quantity) ≤ SUM(sal_trade_item.quantity)`，并在事务内加行锁防止并发超额 |
| BR-05 | 储值消费不透支 | 服务层 + 行锁 | 事务内 `SELECT ... FOR UPDATE` 锁定会员行，校验 `balance + gift_balance ≥ 扣减额` |
| BR-06 | 会员积分不为负 | 同上 | 事务内校验 `points ≥ 抵扣积分` |
| BR-07 | 盘点差异必须可解释 | 服务层校验 | 差异行未填 `diff_reason` 时拒绝提交 |
| BR-08 | 整单优惠不超过上限 | 服务层校验 | 优惠总额 ≤ 商品总额 × `sal.promo_max_rate`，超出部分自动截断 |
| BR-09 | 成本不因后续进货而失真 | 快照字段 | 销售明细锁定 `cost_price` |
| BR-10 | 单据状态流转合法 | 服务层状态机 | 每类单据定义合法状态迁移表，非法迁移直接拒绝 |

### 7.5 事务边界设计

以下操作必须在**单个数据库事务**内完成，任一环节失败则整体回滚：

| 事务 | 涉及的表 | 原子性要求 |
| --- | --- | --- |
| **T1 收银结算** | `sal_trade` + `sal_trade_item` + `sal_trade_payment` + `inv_stock` + `inv_stock_flow` + `inv_batch` + `mem_member` + `mem_point_flow` + `mem_balance_flow` + `sal_session` | 销售单、库存、会员余额、班次汇总必须同时生效，禁止"扣了库存没记销售" |
| **T2 采购收货** | `pur_receipt` + `pur_receipt_item` + `pur_order` + `pur_order_item` + `inv_stock` + `inv_stock_flow` + `inv_batch` + `prd_product.avg_cost` + `pur_supplier.balance_payable` | 收货单、库存增加、成本重算、订单状态必须一致 |
| **T3 盘点调整** | `inv_check` + `inv_check_item` + `inv_stock` + `inv_stock_flow` | 差异行的库存调整与流水必须成对出现 |
| **T4 会员充值** | `mem_member` + `mem_balance_flow` | 余额与流水必须同时写入，否则资金对不上 |
| **T5 销售退货** | `sal_return` + `sal_return_item` + `inv_stock` + `inv_stock_flow` + `sal_trade.status` + `mem_member` + `mem_point_flow` + `mem_balance_flow` | 库存回滚、毛利回冲、积分与储值回退必须一致 |
| **T6 交班对账** | `sal_session` + `sal_trade`（只读汇总） | 班次状态与汇总数据一致 |

**隔离级别选择**：采用 MySQL 默认的 `REPEATABLE READ`。对于库存扣减与会员余额扣减这类"读-改-写"场景，显式使用 `SELECT ... FOR UPDATE` 加行锁，避免 RR 级别下的写偏斜导致超卖或透支。

## 8 典型业务数据流

### 8.1 收银结算（事务 T1）

```
① 扫码/搜索 ──► prd_barcode（按 barcode 索引精确定位）
                    或 prd_product（按 product_name 模糊匹配）
                        │
② 加入购物车 ◄──────────┘  取价顺序：促销价 > 会员价 > 零售价
   （前端暂存，不落库）        命中促销则记录 pro_promotion.id
                        │
③ 识别会员 ──► mem_member（按 phone 索引）
              带出 level_id、discount_rate、balance、points、gift_balance
                        │
④ 结算提交（幂等键 request_id）
   ├── 校验 sal_trade.request_id 是否已存在 ──► 唯一索引拦截重复提交
   ├── INSERT sal_trade            （主单：金额、优惠、成本、毛利）
   ├── INSERT sal_trade_item × N   （明细：快照商品名、锁定 cost_price）
   ├── INSERT sal_trade_payment × M（支付：支持现金+微信+储值混合）
   ├── UPDATE inv_stock            （按 store_id+product_id 扣减，行锁）
   │   └── INSERT inv_stock_flow   （销售出库流水，记录 before/after 库存）
   ├── UPDATE inv_batch.remain_qty （按先进先出拣选批次）
   ├── IF 会员消费：
   │   ├── UPDATE mem_member       （total_consume、consume_count、points、last_consume_at）
   │   ├── INSERT mem_point_flow   （积分获取流水）
   │   └── IF 使用储值：UPDATE mem_member.balance/gift_balance + INSERT mem_balance_flow
   └── UPDATE sal_session          （班次汇总：金额、笔数、各支付方式金额）
                        │
⑤ COMMIT ──► 返回单号、找零、打印数据包
                        │
⑥ 异步：打印小票（ESC/POS）、刷新收银台关联推荐（bi_recommend_cache）
```

**关键设计点**：步骤 ④ 的所有写操作共用一个事务，库存扣减必须在会员余额扣减之前完成（先扣货再扣钱），若任一环节失败则全部回滚，顾客不会出现"钱扣了货没出"的情况。

### 8.2 采购收货与成本重算（事务 T2）

```
① 定位采购单 ──► pur_order（按 order_no 唯一索引）+ pur_order_item（待收明细）
                        │
② 录入实收数量（支持部分收货、超收需授权）
   校验：receive_qty ≤ quantity - received_qty
                        │
③ 写单据
   ├── INSERT pur_receipt       （收货单主表）
   └── INSERT pur_receipt_item  （含 batch_no、production_date、expiry_date）
                        │
④ 库存与成本（核心）
   ├── UPDATE inv_stock SET quantity = quantity + receive_qty
   │           WHERE store_id = ? AND product_id = ?       ← 行锁
   ├── 重算移动加权平均成本：
   │     new_avg_cost = (原库存数量 × 原avg_cost + 本次入库数量 × 本次进价)
   │                    ÷ (原库存数量 + 本次入库数量)
   │   UPDATE inv_stock.avg_cost
   │   UPDATE prd_product.avg_cost          ← 冗余同步
   ├── INSERT inv_stock_flow（采购入库流水，记录 before/after 库存与单位成本）
   └── IF 保质期商品：INSERT inv_batch（生成批次与到期日）
                        │
⑤ 回写采购单状态
   ├── UPDATE pur_order_item.received_qty += receive_qty
   ├── UPDATE pur_order.status = PARTIAL / RECEIVED / FINISHED
   └── UPDATE pur_supplier.balance_payable += total_amount   ← 应付累计
                        │
⑥ COMMIT
```

**成本公式的边界处理**：当原库存为 0 或负（允许负库存场景）时，公式退化为"直接取本次进价"；当本次入库数量为 0 时不重算成本，避免除零。

### 8.3 库存盘点（事务 T3）

```
① 创建盘点单 ──► INSERT inv_check（status = DRAFT）
   同时冻结账面快照：
   INSERT inv_check_item
     SELECT product_id, quantity AS book_qty, quantity AS snapshot_qty
       FROM inv_stock WHERE store_id = ? AND <盘点范围条件>
                        │
② 盘点作业（期间门店可正常销售）
   ├── 销售产生的库存变动照常写 inv_stock_flow
   └── 系统在差异计算时排除"盘点期间变动"，避免把卖出的货误判为盘亏
                        │
③ 录入实盘数量 ──► UPDATE inv_check_item.actual_qty
   计算：diff_qty = actual_qty - snapshot_qty
         diff_rate = |diff_qty| / snapshot_qty
         profit_loss = diff_qty × cost_price
   校验：diff_qty ≠ 0 时必须填 diff_reason，否则拒绝提交
                        │
④ 提交审核 ──► status = SUBMITTED，需 MANAGER 及以上权限
                        │
⑤ 审核通过（事务）
   ├── FOR EACH diff_qty ≠ 0 的行：
   │   ├── UPDATE inv_stock.quantity = 实盘数（行锁）
   │   └── INSERT inv_stock_flow（flow_type = CHECK_ADJUST，
   │                              direction 由差异正负决定）
   ├── UPDATE inv_check.status = AUDITED
   └── 计算并记录本次盘点损益金额
                        │
⑥ COMMIT ──► 进销存报表随即平衡：期初 + 本期入 − 本期出 = 期末
```

**快照字段的必要性**：若不用 `snapshot_qty` 而直接用当前 `inv_stock.quantity` 作账面数，则在盘点期间发生的销售会导致"盘点开始时与结束时账面数不同"，差异将无法解释。快照字段使盘点基准在时间上被冻结。

### 8.4 会员储值与积分（事务 T4）

```
【充值】
① INSERT mem_balance_flow（flow_type = RECHARGE，amount = 充值额）
② IF 有赠送：
   INSERT mem_balance_flow（flow_type = GIFT，gift_amount = 赠送额）
③ UPDATE mem_member SET balance += 充值额, gift_balance += 赠送额

【消费扣款】（优先级：赠送余额优先扣，其次本金）
① 计算：先扣 gift_balance，不足部分再扣 balance
② UPDATE mem_member（两个余额字段同步更新）
③ INSERT mem_balance_flow（flow_type = CONSUME，同时记录两组 before/after 余额）

【积分获取】
① 按 prd_product.is_allow_point 过滤不参与积分的商品
② 积分 = 参与积分金额 × mem.point_rate，向下取整
③ UPDATE mem_member.points += 积分
④ INSERT mem_point_flow（flow_type = EARN，记录 before/after 积分）

【积分抵扣】
① 校验：used_points ≤ points，且抵扣金额 ≤ 应收 × mem.point_deduct_limit
② UPDATE mem_member.points -= used_points
③ INSERT mem_point_flow（flow_type = DEDUCT）
```

**本金与赠送分开记账的原因**：若把充值 100 元送 20 元合并记为余额 120 元，当顾客要求退款时无法判断该退多少。分开两个字段后，退款规则明确为"只退本金未消费部分"，赠送余额在退款时清零，从数据结构上杜绝了"充值—退款"套取赠送金额的漏洞。

### 8.5 关联规则挖掘的数据流

```
① 生成分析任务 ──► INSERT bi_analysis_task（status = PENDING，params_json 记录参数）
                        │
② 抽取事务集（只读）
   SELECT t.trade_no, i.product_id
     FROM sal_trade t JOIN sal_trade_item i ON i.trade_id = t.id
    WHERE t.status = 'FINISHED'
      AND t.trade_time >= DATE_SUB(NOW(), INTERVAL 90 DAY)
   按 trade_no 聚合，每个单号得到一个商品集合（项集）
                        │
③ 过滤
   ├── 排除退货单、作废单、赠品行（amount = 0）
   ├── 排除出现频次 < min_item_count 的低频商品（降噪）
   └── 构造 one-hot 矩阵（pandas）
                        │
④ 挖掘（mlxtend）
   ├── 频繁项集：frequent_itemsets(df, min_support, max_len, use_colnames=True)
   └── 关联规则：association_rules(fi, metric='confidence', min_threshold=0.3)
   过滤：lift > min_lift
                        │
⑤ 落库
   ├── DELETE bi_association_rule WHERE task_id = 本次任务
   ├── INSERT bi_association_rule × N（支持度、置信度、提升度、杠杆率、确信度）
   ├── 生成建议动作 suggestion（按规则类型映射：捆绑/陈列/套餐/推荐）
   └── 生成业务解读 interpretation（自然语言文本）
                        │
⑥ 刷新推荐缓存
   DELETE bi_recommend_cache
   INSERT bi_recommend_cache
     SELECT 前件商品, 后件商品, lift × confidence AS score, reason
       FROM bi_association_rule ORDER BY score DESC
   （每个商品保留 TOP 3）
                        │
⑦ UPDATE bi_analysis_task（status = SUCCESS，cost_ms、rule_count、result_summary）
```

**性能设计要点**：步骤 ② 的抽取使用单条 SQL 完成聚合，避免在 Python 层逐单循环；步骤 ⑤ 先按 `task_id` 删除旧规则再批量插入，保证同一任务的规则要么全有要么全无；步骤 ⑥ 的推荐缓存让收银台的推荐接口只需走一次索引查询，满足 100ms 的响应要求。

## 9 性能与优化设计

### 9.1 查询性能优化

| 优化手段 | 应用点 | 效果 |
| --- | --- | --- |
| 覆盖索引 | 收银台扫码：`prd_barcode.uk_barcode` 直接定位商品 | 单条查询 < 5ms |
| 复合索引最左前缀 | `idx_store_time(store_id, trade_time)` 服务销售日报 | 避免全表扫描 |
| 聚合表预计算 | `bi_daily_stat` 承担经营看板全部指标 | 看板首屏 ≤ 3s，从百万行扫描降为几十行 |
| 冗余汇总字段 | `mem_member.total_consume`、`pur_supplier.balance_payable` | 会员列表、供应商对账免去聚合查询 |
| 分页优化 | 深度分页改用"上次最大 id"游标方式 | 避免 `LIMIT 100000, 20` 的性能悬崖 |
| 避免 `SELECT *` | 服务层按 DTO 精确取列 | 减少网络传输与内存占用 |

**一个具体的分页陷阱**：商品列表第 1000 页若写成 `SELECT * FROM prd_product LIMIT 19980, 20`，MySQL 需要先扫描并丢弃 19980 行。优化做法是记录上一页最后一行的 id，改为 `WHERE id > ? ORDER BY id LIMIT 20`，使复杂度从 O(offset) 降为 O(1)。

### 9.2 并发与锁设计

| 场景 | 锁策略 | 说明 |
| --- | --- | --- |
| 库存扣减 | 行锁 `SELECT ... FOR UPDATE` | 同一商品并发结算时串行化，防止超卖 |
| 会员余额扣减 | 行锁 `SELECT ... FOR UPDATE` | 防止同一会员卡在多台收银机并发透支 |
| 单号生成 | 独立序列表或 `INSERT ... ON DUPLICATE KEY UPDATE` | 避免 `SELECT MAX(no) + 1` 的并发重号 |
| 关联分析 | 无锁（只读快照 + 全量覆盖写） | 后台任务，允许结果短暂为空 |
| 报表查询 | 不加锁，走 MVCC 快照读 | 报表不阻塞收银写操作 |

**关于死锁的预防**：T1 收银事务会同时更新 `inv_stock` 与 `mem_member`。若两个并发事务以不同顺序获取这两把锁，可能形成死锁。约束措施是**统一加锁顺序**：先按 `product_id` 升序获取库存锁，再获取会员锁，使所有事务的加锁路径一致，从结构上消除循环等待条件。

### 9.3 性能指标对照

以下为数据库层面的设计目标，与需求文档 NFR-P 系列指标对应：

| 需求编号 | 指标 | 数据库侧保障手段 |
| --- | --- | --- |
| NFR-P-01 | 收银结算 ≤ 500ms | 单事务内约 10~15 次写操作，全部走主键/唯一索引；无表级锁 |
| NFR-P-03 | 条码检索 ≤ 200ms | `prd_barcode.uk_barcode` 唯一索引，单条查询 |
| NFR-P-04 | 库存查询 ≤ 800ms | `inv_stock` 单表分页 + `idx_product`，单门店约 8000 行 |
| NFR-P-05 | 会员尾号检索 ≤ 300ms | `mem_member.idx_phone_suffix` 索引，配合 `LIKE '%8866'` 的右匹配 |
| NFR-P-06 | 看板首屏 ≤ 3s | 全部指标取自 `bi_daily_stat`，单次查询返回几十行 |
| NFR-P-09 | 关联挖掘 ≤ 60s | SQL 层完成事务集聚合，Python 层仅做算法计算；结果批量插入 |
| NFR-P-10 | 10 终端并发收银 | 行级锁 + 统一加锁顺序，无表锁与死锁 |

## 10 安全设计

### 10.1 数据访问安全

| 编号 | 措施 | 实现 |
| --- | --- | --- |
| DS-01 | 最小权限原则 | 应用连接使用独立数据库账号，仅授予本库的 DML 权限，不给 `DROP` / `GRANT` 权限 |
| DS-02 | 禁止生产库直连 | 生产环境数据库不开放公网端口，仅允许应用服务器内网访问 |
| DS-03 | 参数化查询 | 全部数据访问通过 SQLAlchemy ORM 或参数化语句，杜绝 SQL 拼接 |
| DS-04 | 行级数据隔离 | 通过 `store_id` 过滤实现多门店数据隔离，由服务层统一注入过滤条件 |
| DS-05 | 视图脱敏 | 为报表场景建立脱敏视图（手机号掩码），避免直接暴露原表 |

### 10.2 敏感数据保护

| 数据类别 | 字段 | 保护措施 |
| --- | --- | --- |
| 登录凭证 | `sys_user.password_hash` | bcrypt 加盐哈希，不可逆；数据库泄露也无法还原明文 |
| 会员手机号 | `mem_member.phone` | 列表与导出场景掩码显示（`138****8866`），导出需额外权限并记日志 |
| 会员储值 | `mem_member.balance` | 任何变动必须生成 `mem_balance_flow` 流水，可逐笔追溯 |
| 支付流水号 | `sal_trade_payment.pay_no` | 仅授权角色可查看完整值 |
| 备份文件 | `backup_*.sql.gz` | 加密存储，仅 ADMIN 可下载 |
| 操作留痕 | `sys_operation_log.before_value/after_value` | 资金相关操作强制记录前后值 |

**重要说明**：会员手机号保留了原始明文（而非加密存储），原因是收银场景需要"输入尾号 4 位即检索"，加密后无法支持模糊匹配。折中方案是**存储明文 + 展示脱敏 + 访问审计**：数据库层不加密，但所有读取手机号的接口都必须通过权限校验，且导出行为写入操作日志。这一取舍在需求文档 NFR-S-07 中已明确。

### 10.3 备份与恢复

见 5.4 节。补充数据库层面的具体命令：

```bash
# 全量备份（含结构与数据）
mysqldump -uroot -p --single-transaction --routines --triggers \
  --default-character-set=utf8mb4 community_supermarket | gzip > backup_$(date +%Y%m%d%H%M%S).sql.gz

# 查看当前 binlog 位点（用于增量恢复起点）
mysql -uroot -p -e "SHOW MASTER STATUS;"

# 恢复
gunzip < backup_20260915233000.sql.gz | mysql -uroot -p --default-character-set=utf8mb4 community_supermarket
```

`--single-transaction` 参数保证备份过程中不锁表，门店可以正常营业。

### 10.4 审计设计

`sys_operation_log` 表承担审计职责，其设计有两个要点：

1. **只增不改**：该表不提供 UPDATE 与 DELETE 接口，应用连接账号对该表只授予 INSERT 与 SELECT 权限，从权限层面保证日志不可篡改。
2. **完整的变更快照**：`before_value` 与 `after_value` 两个 JSON 字段记录操作前后的完整数据，使任何一次价格修改、库存调整、权限变更都可被完整还原。

必须记录日志的操作清单：商品价格修改、促销规则增删改、退货、单据作废、盘点调整、库存手工调整、权限变更、数据备份与恢复、系统参数修改、会员储值操作。

| 外键约束 | 86 条 | 覆盖全部主外键引用关系 |

| 普通索引 | 52 个 | 覆盖高频查询路径 |

| 主要联系 | 24 组 | 含 9 组多对多联系（独立成表） |

### 11.2 设计特点

**（1）流水驱动，账实可验。** 库存不以"当前数量"为唯一依据，而以 `inv_stock_flow` 的完整流水为真相源，每条流水记录变动前后值。这意味着任意时点的库存都能被独立复算，解决了传统收银软件"库存对不上、说不清原因"的通病。

**（2）快照留痕，历史不变。** 销售明细冗余存储商品名称、规格、单位与成本价。商品改名、改价、进货成本波动都不会改变历史单据的呈现与历史毛利的计算，这对经营者复盘月度经营效果至关重要。

**（3）资金双轨，堵住漏洞。** 会员储值分为本金与赠送两个独立字段，配合独立的 `mem_balance_flow` 流水表，使"充值送金额—消费—退款"全链路可逐笔核对，从数据结构上封堵了套取赠送金额的可能。

**（4）业务键与代理键分离。** 所有表使用无业务含义的自增主键，业务编码（商品编码、单号、条码）作为独立字段加唯一索引。既保证了业务唯一性，又使编码规则的调整不影响任何外键关系。

**（5）性能与规范的显式权衡。** 本设计在 8 处引入了有意的反范式冗余字段（见 4.2 节表格），全部采用"写入时同事务更新"策略保证一致性，并在文档中明确记录取舍理由。这种"知道自己在违反什么范式、为什么违反、如何补偿"的设计方式，比机械追求 3NF 更符合工程实际。

**（6）为算法能力预留结构。** `bi_analysis_task` 记录每次挖掘的参数与耗时，`bi_association_rule` 保存完整的规则指标与业务解读文本，`bi_recommend_cache` 让收银台推荐走内存级查询。这三个表使"购物篮关联分析"这一技术特色不是论文里的孤立章节，而是真正嵌入业务闭环。

### 11.4 局限与后续演进

**当前设计的已知局限**：

1. **不含多组织架构**：门店之间是并列关系，没有集团—区域—门店的层级结构，因此无需组织树表。若未来发展为 20 家以上连锁，需要补充组织架构表与权限的数据范围模型。
2. **单库单表**：所有数据在一个库中，未做分库分表。按 9.4 节的容量估算，单店 3 年数据量在 8GB 以内，单机足以支撑；超过 500 万行的明细表建议按时间分区。
3. **成本核算方法固定为移动加权平均**：`sys_config.inv.cost_method` 预留了配置位，但一期只实现该方法。先进先出、个别计价等方法需要增加批次级成本明细表。
4. **支付为登记模式**：`sal_trade_payment` 记录支付方式与金额，但未对接微信/支付宝的统一下单与回调接口，`pay_no` 字段已为日后对接预留。
5. **无操作日志的归档表**：日志目前与业务表同库，长期看应迁移至独立的日志库或时序存储。

**演进路线建议**：

| 阶段 | 目标 | 数据库侧工作 |
| --- | --- | --- |
| 二期 | 接入真实支付 | 扩展 `sal_trade_payment.pay_no` 的索引，新增支付回调记录表 |
| 二期 | 供应链协同 | 补充采购申请单、到货计划表 |
| 三期 | 多门店连锁 | 补充组织架构表，`store_id` 之上加 `org_id` 层级 |
| 三期 | 数据仓库 | 将 `bi_daily_stat` 扩展为星型模型（事实表 + 维度表），支撑多维分析 |
| 四期 | 实时推荐 | 引入 Redis 承载 `bi_recommend_cache`，MySQL 保留持久化副本 |
