## 1 项目概述

### 1.1 项目背景

社区超市是零售业态中数量最多、离居民最近的一类经营主体，通常营业面积 100～500 平方米，
经营品类集中于生鲜果蔬、粮油调味、休闲食品、日用百货等高频刚需商品，员工规模 3～15 人，
配置 1～2 台收银机。

这类门店处于一个尴尬的位置：

| 现状 | 问题 |
| --- | --- |
| 管理需求真实存在 | 但传统商超 ERP 功能庞大、部署沉重、按年收费，投入产出比极低 |
| 经营决策依赖经验 | 交易数据留在收银机本地，既不能形成经营看板，也不能反哺采购与陈列决策 |
| 人员流动性极高 | 收银员多为兼职或临聘，系统必须在半小时内上手 |

**结论**：社区超市需要的不是"功能齐全的 ERP"，而是**轻量、够用、能立刻上手**的管理系统。

### 1.2 项目目标

围绕"进—销—存—会—析"五个环节，构建一套部署简单、操作直观、数据闭环的销售管理系统：

| 序号 | 目标 | 衡量方式 |
| --- | --- | --- |
| G1 | **收银快** | 扫码到加购的响应 P95 ≤ 200ms；结算 P95 ≤ 500ms；全流程可不用鼠标（快捷键） |
| G2 | **账目清** | 任意时点库存可独立复算；每笔库存变动可追溯到来源单据；进销存勾稽恒等式成立 |
| G3 | **权限明** | 三级权限（菜单级 / 按钮级 / 数据范围）；一张角色表能覆盖"一人多岗" |
| G4 | **决策有依据** | 提供经营看板、报表体系，并通过购物篮关联分析反哺商品陈列与促销 |
| G5 | **部署轻** | 单机可跑，不依赖 Redis / 消息队列等外部中间件 |

### 1.3 项目范围

**纳入范围**

| 域 | 内容 |
| --- | --- |
| 认证与权限 | 登录、验证码、JWT 双令牌、RBAC 三级授权、操作与登录日志 |

| 库存 | 实时库存、库存流水、批次与保质期、盘点、报损、门店调拨、三类预警 |
| 销售 | 收银台（扫码、称重、会员、混合支付、促销试算、关联推荐）、挂单、退货、作废、小票、交班 |
| 会员 | 会员档案、等级与折扣、储值（本金/赠送双轨）、积分、会员标签、消费档案 |

| 报表 | 经营看板、销售日报、时段分析、商品排行、品类分析、毛利分析、滞销分析、进销存勾稽、采购/会员/收银员报表、导出 |
| 智能分析 | 关联规则挖掘（Apriori / FP-Growth）、规则业务解读、采纳生成促销、算法性能对比、销售预测、智能补货 |
| 系统管理 | 用户、角色权限树、系统参数、日志查询、备份与恢复、运行信息 |

**不纳入范围（一期）**

| 项 | 原因 |
| --- | --- |
| 移动端 App / 小程序 | 门店场景以 PC 收银为主，一期不做 |
| 热敏打印机驱动对接 | 走浏览器打印，避免硬件依赖 |
| 线上商城 / 到家配送 | 偏离"门店管理"核心 |
| 多仓 / 中央仓 | 社区超市多为单店或 2～5 家小连锁，无中心仓需求 |
| 财务总账 | 只做业务账（应收应付），不做会计科目与凭证 |

### 1.4 术语约定

| 术语 | 说明 |
| --- | --- |
| SKU / SPU | 最小库存单位 / 标准商品单元（同款不同规格的聚合） |
| 进销存 | 采购进货、销售出货、库存结存三者的合称 |
| 流水驱动 | 以"变动流水"为库存的唯一真相源，库存表只是冗余快照 |
| 快照冗余 | 交易明细冗余商品名、成本价等属性，冻结业务发生时的状态 |
| 移动加权平均 | 每次入库后重算单位成本的存货计价方法 |
| 临期商品 | 距保质期截止日小于阈值（默认 30 天）的商品 |
| 购物篮分析 | 通过关联规则挖掘发现商品共购关系（Apriori / FP-Growth） |

## 2 行业与需求分析

### 2.1 社区超市业态特征

项目的功能取舍不是凭空决定的，而是由社区超市的业态特征推导而来：

| 编号 | 特征 | 对系统的要求 |
| --- | --- | --- |
| C-01 | 营业面积小（100～500㎡），SKU 少而精（通常 1,500～3,000 个） | 商品管理要"轻"，不需要复杂的商品属性体系 |
| C-02 | 生鲜占比高（30%～50%） | **必须支持称重商品、保质期与批次管理** |
| C-03 | 客单价低（15～40 元）、笔数多 | 收银速度是第一要务，操作步骤越少越好 |
| C-04 | 员工少（3～15 人）且一人多岗 | **权限模型必须支持一人多角色**，不能一人一号一号一职 |
| C-05 | 人员流动快，收银员常为兼职 | 系统必须半小时内上手，全流程可不用鼠标 |
| C-06 | 价格调整频繁（促销、临期降价） | 价格变更要留痕，促销要能快速配置与试算 |
| C-07 | 保质期管理是刚需，损耗率高 | 临期预警、报损登记、先进先出 |
| C-08 | 客源以周边熟客为主 | 会员体系以"储值 + 积分"为核心，而非复杂的等级权益 |
| C-09 | 促销靠经验和手工海报 | 促销引擎要能覆盖常见玩法，并支持效果复盘 |
| C-10 | 进销存协同弱，缺货与积压并存 | 库存预警、智能补货建议 |
| C-11 | 经营数据沉淀为"死账" | 经营看板 + 报表 + 购物篮分析，把数据变成决策依据 |

### 2.2 核心痛点分析

#### 痛点一：管理需求真实存在，但买不起也用不动 ERP

传统商超 ERP 按年收费，功能庞大，部署需要专业 IT 支持。对只有一两台收银机的社区超市而言：

- **经济上**：年费可能超过门店一个月净利润；
- **能力上**：没人会配置，供应商也不会为单店做实施；
- **功能上**：80% 的功能用不上（多仓、中央配送、复杂财务）。

**本项目对策**：单机可部署、零外部中间件依赖、功能围绕门店实际业务裁剪。

#### 痛点二：经营决策依赖经验，数据沉淀为"死账"

绝大多数社区超市的收银机只做"收钱"：

```
交易数据 → 存在本地 → 无人使用 → 过期清理
```

结果是"进货靠拍脑袋、库存靠目测"，缺货与积压同时存在。

**本项目对策**：经营看板（今日/昨日/本月指标 + 30 天趋势 + 三类预警 + 待办）、
完整报表体系、**购物篮关联分析**（发现共购关系 → 直接生成促销）。

#### 痛点三：人员流动性高，培训成本敏感

收银员多为兼职或临聘，任何需要多级菜单、复杂操作的交互都会直接拉低收银效率。

**本项目对策**：收银台全屏布局、快捷键覆盖全流程（F2 聚焦 / F4 会员 / F5 挂单 / F8 结算 / F9 取消）、
扫码回车即加购、常用商品快捷区。

### 2.3 现有方案对比

| 方案 | 优点 | 缺点 | 适配度 |
| --- | --- | --- | --- |
| 传统商超 ERP | 功能全、稳定 | 贵、重、需实施、功能过剩 | ✗ |
| SaaS 收银软件 | 便宜、开箱即用 | 数据在第三方、定制难、断网不可用 | △ |
| Excel 手工记账 | 零成本 | 易错、无协同、无法沉淀分析 | ✗ |
| **本系统** | 轻量、可控、数据自主、含智能分析 | 需自行部署维护 | **✓** |

**结论**：本系统填补的是"比 Excel 强、比 ERP 轻"的空白区间。

### 2.4 需求分析结论

| 结论 | 说明 |
| --- | --- |
| 功能应"够用即好" | 宁缺毋滥，每个功能都要能对应到业务动作 |
| 性能优先级：收银 > 库存 > 报表 | 收银卡顿直接影响赚钱 |
| 数据必须可追溯 | 库存、资金、权限三类变动都要留痕 |
| 架构必须轻 | 不引入 Redis / MQ，降低部署与运维门槛 |

## 3 可行性分析

### 3.1 技术可行性

| 技术点 | 方案 | 成熟度 | 风险 |
| --- | --- | --- | --- |
| Web 后端框架 | FastAPI（异步、Pydantic 强校验、自动 OpenAPI） | 成熟 | 低 |
| ORM | SQLAlchemy 2.0 | 成熟 | 低 |
| 数据库 | MySQL 8.0（InnoDB、事务、JSON 字段） | 成熟 | 低 |
| 前端框架 | Vue 3.5（Composition API + `<script setup>`） | 成熟 | 低 |
| UI 组件库 | Element Plus 2.9 | 成熟 | 低 |
| 图表 | ECharts 5.6 | 成熟 | 低 |
| 关联规则挖掘 | mlxtend（Apriori / FP-Growth）+ pandas | 成熟 | 低 |
| 认证 | JWT 双令牌 + bcrypt | 成熟 | 低 |

**关键技术可行性论证**

1. **关联规则挖掘**：`mlxtend` 提供了开箱即用的 `apriori` / `fpgrowth` / `association_rules`，
   无需自行实现算法；数据规模（数万条交易）在单机内存中可轻松处理。
2. **库存一致性**：通过数据库事务 + 条件更新（`UPDATE ... WHERE quantity >= ?`）可保证不超卖，
   无需分布式锁。
3. **性能目标**：单店日均数百单，MySQL 单表配合索引完全能满足 P95 ≤ 500ms 的结算要求。

**结论**：全部关键技术均有成熟开源方案，无技术攻关型难点。

### 3.2 经济可行性

| 项 | 成本 |
| --- | --- |
| 软件许可 | 0（全部使用开源组件） |
| 服务器 | 本地部署：利用门店现有 PC；云部署：约 60～100 元/月（入门级） |
| 数据库 | MySQL Community Edition，0 |
| 部署维护 | 单机部署，一次配置长期运行 |
| 培训成本 | 收银员约 30 分钟，管理员约 2 小时 |

**收益（对门店）**

| 收益点 | 说明 |
| --- | --- |
| 减少损耗 | 临期预警 + 报损登记，降低生鲜损耗 |
| 减少缺货 | 库存预警 + 智能补货建议 |
| 提升收银效率 | 快捷键操作，缩短单笔交易时间 |
| 减少人工对账 | 交班自动汇总，现金差异强制说明 |
| 提升复购 | 会员储值与积分 |

**结论**：投入极低，收益明确，经济上完全可行。

### 3.3 操作可行性

| 角色 | 上手难度 | 设计对策 |
| --- | --- | --- |
| 收银员 | 低 | 全屏收银台、快捷键、扫码回车即加购、常用商品快捷区 |
| 库管员 | 中 | 收货/盘点按单据驱动，必填项校验前置 |
| 店长 | 中 | 看板与报表图形化，异常数据标红 |
| 管理员 | 中高 | 权限树可视化勾选，参数带说明文字 |

**结论**：交互设计已针对"人员流动快"做了专门优化，操作可行。

### 3.4 时间可行性

项目按 6 个阶段推进（详见第 6 章），工作量集中在"收银主链路"与"数据分析"两块，
其余模块为标准的增删改查，可复用统一的列表页组件与接口约定。

**结论**：在毕业设计周期内可完成。

### 3.5 风险与合规

| 项 | 说明 |
| --- | --- |
| 数据合规 | 会员手机号等敏感信息导出时脱敏；密码 bcrypt 哈希存储 |
| 数据安全 | 操作日志记录变更前后值；备份与恢复机制 |

### 3.6 可行性结论

**技术、经济、操作、时间四个维度均可行，项目立项成立。**

## 4 需求分析

### 4.1 用户角色

| 角色 | 编码 | 数据范围 | 核心职责 | 关键权限 |
| --- | --- | --- | --- | --- |
| 系统管理员 | `ADMIN` | 全部门店 | 用户、角色、权限、参数、备份、日志 | 全部 |
| 店长 | `MANAGER` | 本门店 | 商品价格、促销、采购审批、全部报表 | 除系统设置外全部 |
| 收银员 | `CASHIER` | 仅本人 | 收银结算、会员办理、退货申请、交班 | 收银台、交班、会员查看 |
| 库管员 | `STOCKER` | 本门店 | 入库、出库、盘点、报损、临期处理 | 商品查看、采购收货、库存全套 |
| 采购员 | `PURCHASER` | 本门店 | 供应商维护、采购下单、收货、对账 | 采购全套、采购报表 |

> **一人多岗**：社区超市常见"收银员兼理货"，因此权限模型支持一个用户绑定多个角色，权限取并集
> （演示数据中 `buyer01` 即是"采购员 + 店长"）。

### 4.2 核心业务流程

#### 4.2.1 收银结算（最高频）

```
扫码/输入编码 → 解析商品 → 加入购物车
      ↓
（可选）识别会员 → 取会员价
      ↓
实时促销试算 → 显示优惠明细
      ↓
（可选）积分抵扣 / 抹零
      ↓
选择支付方式（支持混合支付）→ 结算
      ↓
[同一事务] 写销售单 + 明细 + 支付 + 扣库存 + 写流水 + 会员权益变动
      ↓
打印小票 → 完成
```

**异常分支**：商品不存在 / 商品已停用 / 库存不足 / 支付金额不符 / 会员余额或积分不足。

#### 4.2.2 采购入库

```
创建采购订单 → 店长审核 → 到货收货
      ↓
录入实收数量、单价、批次与到期日
      ↓
[同一事务] 写收货单 + 增加库存 + 写库存流水 + 重算移动加权平均成本
```

#### 4.2.3 库存盘点

```
创建盘点单 → [冻结账面快照]
      ↓
逐项录入实盘数
      ↓
差异项必须填写原因 → 提交审核
      ↓
审核通过 → [同一事务] 调整库存 + 写盘点调整流水
```

#### 4.2.4 智能分析闭环

```
积累交易数据
      ↓
配置挖掘参数（支持度/置信度/提升度）→ 触发异步任务
      ↓
产出关联规则 + 业务解读
      ↓
（两条出口）① 收银台实时关联推荐  ② 一键采纳生成促销活动
      ↓
复盘促销效果 → 反哺下一次分析
```

| **性能** | 条码解析 P95 ≤ 200ms；结算 P95 ≤ 500ms；看板 ≤ 2s；支持 5 个收银台并发 |
| **安全** | 密码 bcrypt 哈希；JWT 双令牌；接口级权限校验；登录失败锁定；导出脱敏 |
| **可靠性** | 资金类接口幂等；结算事务原子性；每日自动备份 |
| **易用性** | 收银全流程可不用鼠标；表单校验前置提示；异常数据可视化标红 |
| **可维护性** | 分层架构；接口与数据模型严格对应；统一响应体与错误码 |
| **兼容性** | Chrome / Edge 现代浏览器；分辨率 ≥ 1366×768 |

### 4.5 需求优先级

| 优先级 | 定义 | 模块 |
| --- | --- | --- |
| P0 必须 | 不做则系统不可用 | 认证权限、商品、库存、收银结算、基础报表 |
| P1 重要 | 影响核心体验 | 采购、会员、促销、交班、盘点 |
| P2 增强 | 提升竞争力 | 智能分析、销售预测、智能补货、报损调拨 |

## 5 技术方案分析

### 5.1 技术选型论证

#### 5.1.1 为什么选 FastAPI

| 对比项 | FastAPI | Flask | Django |
| --- | --- | --- | --- |
| 异步支持 | 原生 async/await | 需扩展 | 3.1+ 部分支持 |
| 数据校验 | **Pydantic 内置** | 需 marshmallow | 需 DRF Serializer |
| 接口文档 | **自动生成 OpenAPI** | 需扩展 | 需 drf-spectacular |
| 性能 | 高（基于 Starlette） | 中 | 中 |
| 学习曲线 | 平缓 | 平缓 | 陡峭 |
| 与数据科学生态 | **同属 Python，可直接调 pandas/mlxtend** | 同 | 同 |

**关键理由**：本项目需要接入购物篮关联分析（pandas + mlxtend），
FastAPI 处于 Python 生态内，可与分析库无缝协作；Pydantic 强类型校验让"接口契约"与
"数据模型"天然一致，减少前后端对字段的分歧。

#### 5.1.2 为什么选 Vue 3 + TypeScript

| 理由 | 说明 |
| --- | --- |
| Composition API | 收银台、库存等复杂页面逻辑可抽成 composable 复用 |
| TypeScript | 前后端字段对齐，编译期发现字段名不一致（本项目实测有效） |
| Element Plus | 后台管理系统组件齐全，表格/表单/弹窗开箱即用 |
| Vite | 冷启动快，开发体验好 |

#### 5.1.3 为什么选 MySQL

| 理由 | 说明 |
| --- | --- |
| 事务支持 | 结算、收货等多表写入必须原子 |
| 成熟稳定 | 单机部署简单，运维成本低 |
| 窗口函数 | MySQL 8.0 支持，报表聚合更方便 |
| JSON 字段 | 挂单购物车、日志快照可直接存 JSON |

### 5.2 系统架构

```
┌───────────────────────────────────────────────┐
│  前端（Vue 3 + TS + Element Plus + ECharts）    │
│  36 个页面 · 3 套布局 · 动态路由 + 权限守卫       │
└───────────────────┬───────────────────────────┘
                    │ HTTP / JSON（统一响应体）
┌───────────────────▼───────────────────────────┐
│  后端（FastAPI）                                │
│  ┌─────────────────────────────────────────┐  │
│  │ Router 层（128 个接口，按模块划分）        │  │
│  ├─────────────────────────────────────────┤  │
│  │ Service 层（促销引擎、库存、结算、分析）    │  │
│  ├─────────────────────────────────────────┤  │
│  │ Model 层（SQLAlchemy ORM）               │  │
│  └─────────────────────────────────────────┘  │
│  横切：JWT 鉴权 · 权限校验 · 统一响应 · 日志      │
└───────────────────┬───────────────────────────┘
                    │
┌───────────────────▼───────────────────────────┐
│  MySQL 8.0（61 张表 / 8 个数据域）              │
│  流水表（只增）+ 主数据 + 交易 + 分析结果         │
└───────────────────────────────────────────────┘
```

**分层职责**

| 层 | 职责 | 不做什么 |
| --- | --- | --- |
| Router | 参数校验、权限校验、调用 Service、封装响应 | 不写业务逻辑 |
| Service | 业务规则、事务边界、跨表协作 | 不碰 HTTP |
| Model | 表映射、关系定义 | 不写业务逻辑 |

### 5.3 关键技术难点与对策

| 难点 | 风险 | 对策 |
| --- | --- | --- |
| **库存一致性** | 并发收银导致超卖 | 条件更新 `WHERE quantity >= ?`；流水与快照同事务写入 |
| **成本核算** | 进价波动污染历史毛利 | 移动加权平均 + 交易明细成本快照 |
| **促销冲突** | 多促销叠加算错价 | 优先级顺序计算 + 叠加互斥 + 上线前价格试算 |
| **重复结算** | 网络重试导致重复扣款 | `request_id` 唯一索引幂等 |
| **会员储值套利** | 充值赠送后退款套利 | 本金/赠送双字段分账，退款只退本金 |
| **盘点期间营业** | 正常销售被误判盘亏 | 冻结 `snapshot_qty` 账面快照 |
| **大数据量报表** | 报表查询拖慢收银 | 预聚合表 + 索引优化 + 冷热分离 |
| **权限码不一致** | 菜单缺失且难排查 | 数据库权限码与前端路由逐条核对（已实测零差异） |

### 5.4 与同类方案的技术差异

| 差异点 | 传统收银软件 | 本系统 |
| --- | --- | --- |
| 库存模型 | 只维护库存表 | **流水驱动**，可追溯、可复算 |
| 历史毛利 | 按当前进价计算 | **成本快照**，历史数据不被污染 |
| 会员储值 | 单一余额 | **本金/赠送双轨**，防套利 |
| 数据分析 | 简单统计报表 | **购物篮关联分析** + 实时推荐 + 采纳生成促销 |
| 售前验证 | 无 | **促销价格试算**，避免规则冲突算错价 |
| 部署依赖 | 可能依赖中间件 | **零外部中间件**，单机可跑 |

## 9 结论

### 9.1 分析结论

| 维度 | 结论 |
| --- | --- |
| 需求 | 社区超市的轻量管理需求真实存在，现有方案存在明显的适配空白 |
| 可行性 | 技术、经济、操作、时间四个维度均可行 |
| 技术方案 | 全部关键技术有成熟开源方案，无攻关型难点 |
| 差异化 | 流水驱动库存、成本快照、储值双轨、购物篮分析构成竞争差异 |
| 风险 | 主要风险可控，均有明确应对措施 |

### 9.2 项目建议

**建议立项并按计划推进。** 实施中注意三点：

1. **守住范围**——社区超市的核心是"收银 + 进销存 + 会员"，智能分析是加分项而非必需项，
   优先保证 P0 功能的质量；
2. **守住一致性**——库存与资金是系统的命脉，所有相关操作必须走事务，
   并定期跑勾稽校验；
3. **守住易用性**——收银员的上手速度决定系统能否真正落地，
   任何增加收银操作步骤的需求都要慎重评估。
